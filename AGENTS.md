## 1. Что это за проект

**ZShelper** — автономный локальный ассистент для Windows 10/11, который управляет компьютером
голосом и текстом: ведёт приложения, файлы, документы, медиа, код, музыку, умный дом. Работает
офлайн на своих моделях, ничего не отправляет в облако без разрешения, спрашивает подтверждение
перед необратимыми действиями. Приложение обычное десктопное (как Discord), не браузер и не
вкладка: нативное окно, автозапуск, трей.

Стек зафиксирован: **Tauri 2 + Rust-ядро + React 19 + Fluent UI v9** (`docs/DECISION-STACK.md`).
Продукт полностью бесплатный в работе (локальные модели) и при этом продаётся по подписке —
значит, в нём есть лицензирование и защита от копирования (`docs/LICENSING.md`).

Три слоя, которые нельзя путать:

1. **Реестр действий** (`data/actions.psv`) — *что* система умеет вообще, без привязки к программам.
2. **Профили** (`data/profiles/*.json`) — *как именно* это делается в конкретной программе, утилите
   или классе работы: якоря, шаги, проверка результата.
3. **Каталог приложений** (`data/app_targets.psv`) — *насколько хорошо* мы покрываем каждую
   программу Windows: канал автоматизации, tier, приоритет.

4. **Скиллы** (`data/skills/*.json`) — *как из действий получается работа*: последовательность
   шагов с проверками, критерии «готово», точки подтверждения человеком и запреты. Реестр и
   профили отвечают на «могу нажать», скилл — на «сделай трек», «сдай курсовую», «приведи
   систему в порядок». Это единственный слой, где существует результат.

## 4. Семь рецептов: как добавить что-то, не сломав систему

Все команды выполняются из корня репозитория. После любого изменения — раздел 7.

### 4.1 Добавить действие в реестр

```bash
# строка формата: domain|verb|object|example|how|risk|tier|human|status|notes
echo 'files|проверить|контрольные суммы|сверь файлы по хэшу|SHA-256|R|T0|c|v1|' >> data/actions.psv
python3 tools/actions.py        # пересобирает data/actions.json и docs/ACTIONS.md
python3 tools/audit_actions.py  # проверяет семейства и дырки
```

Правила: `risk` из набора `read | write-local | external | destructive | identity | money`;
`tier` из `T0…T3`; `human` из `c | h | n` (может/должен/никогда). Новый **глагол** требует записи
в `data/verb_families.json`, иначе `audit_actions.py` упадёт с `UNMAPPED VERBS`. Новый **домен**
требует записи в `data/domain_families.json` и (если профиля нет) в `data/domain_profile_policy.json`.

### 4.2 Добавить операцию в существующий профиль

```bash
# открыть data/profiles/<app>.json, добавить объект в "operations"
python3 tools/profiles.py
```

Обязательные поля операции: `name`, `registry`, `steps`, `verify`, `risk`. Шаги могут быть
текстом, `anchor:<имя>`, `hotkey:…`, `menu:…`, `type:…`, `cli:…`, `wait:…`. Внутри шага **нельзя**
писать `anchor:имя → что-то`: парсер увидит в этом ссылку на несуществующий якорь — пиши якорь
отдельным шагом. `risk` не может быть ниже риска строки реестра.

### 4.3 Добавить новый профиль

1. Скопировать структуру из `data/profiles/vlc.json` или `_schema.json`.
2. Заполнить `app`, `exe`, `ui_stack`, `version_seen`, `verified_at`, `anchors`, `operations`.
3. Поставить `"kind"`: `app` (программа), `tool` (утилита без GUI), `system` (класс работы в Windows).
4. `python3 tools/profiles.py` → ноль проблем.

Каждая операция должна отвечать на вопрос «как я узнаю, что получилось» через **независимый**
признак, а не через тот же вызов, который выполнял действие.

### 4.4 Добавить приложение в каталог

```bash
echo 'myapp|My App|Медиа|myapp.exe|uia|B|P2|какой канал и почему' >> data/app_targets.psv
python3 tools/app_targets.py
```

Инвариант проверяется автоматически: **tier A ⇒ профиль существует**. Поэтому либо сначала
профиль, либо tier B/C. Если приложение можно вести через CLI/API — предпочитай его UIA.

### 4.5 Авто-профиль из живого приложения (Windows)

```bash
python tools/uia_probe.py dump --exe MyApp.exe --out dump.json
python tools/uia_probe.py draft --dump dump.json --out data/profile_drafts/myapp.json
# проверить руками, дописать verify и risk, перенести в data/profiles/, поставить verified_at
```

Классификатор скажет `uia | web-in-shell | uia-poor | canvas`. `canvas` — это tier C (визуальный
агент), не пытайся искать кнопки по имени в OpenGL-приложении.

### 4.6 Добавить скилл (работу, а не операцию)

Брать нужно не «домен целиком», а работу, которую человек формулирует одной фразой.

1. Скопировать структуру из `data/skills/system-tuneup.json` (или `invoice-cycle.json`).
2. Заполнить `id` (= имя файла), `title`, `phrases` (как это говорит человек), `scope`, `inputs`,
   `outputs`, `domains`, `profiles`, `time`, `risk`.
3. Шаги: `steps[]` — `step`, `actions` (ссылки `domain|verb[|object]` на **существующие** строки
   реестра), `verify` (как узнать, что шаг получился).
4. `done` — критерии результата; `checkpoints` — где обязано быть подтверждение человека
   (обязательны, если хоть один шаг `destructive`/`external`/`money`/`identity`);
   `refuse` — что скилл не делает даже по просьбе; `limits` — честная граница.
5. `python3 tools/skills.py` → `docs/SKILLS.md`, ноль ошибок.

Валидатор проверяет, что `domains` совпадают с доменами реально использованных действий, а
заявленный `risk` — с максимумом риска по реестру. Скилл без `done` — это не скилл, а список дел.

### 4.7 Добавить что-то в экосистему (MCP, модель, коннектор, канал)

Экосистема — это **не реестр**: там лежит то, что существует снаружи, с пометкой, проверено ли оно.

1. Найти запись в `research/` (там 1461 MCP-сервер, 347 Agent Skills, 96 агентов, 880 пакетов) или
   в документации вендора/протокола.
2. Добавить в `data/ecosystem/_curated/<каталог>.json` (или расширить селектор в
   `tools/build_ecosystem.py`, если источник — vault).
3. Поставить `status: "candidate"` и `needs_check: true`. **Проверенным** запись становится только
   после проверки лицензии, запуска на Windows, канала (CLI/API/MCP) и способа проверки результата.
4. `python3 tools/build_ecosystem.py && python3 tools/ecosystem.py`.

Правило: `candidate` — это заявка, а не инструмент. Десять тысяч MCP-серверов не делают
ассистента, который умеет работать: путь от каталога до умения идёт через строку реестра,
профиль и скилл.

## 5. Инварианты и запреты (нарушение = красный CI)

1. Фича существует ↔ есть строка реестра **и** тест-кейс. Операция профиля без строки реестра — баг.
2. Профиль **не может занизить риск** относительно реестра.
3. У каждой операции есть `verify`. «Нажал» ≠ «получилось».
4. Домен без профиля обязан быть в `data/domain_profile_policy.json` (очередь или решение).
5. Все генерируемые файлы коммитятся; CI падает, если они устарели.
6. Новый глагол без семейства — падение сборки.
7. Скилл без критериев результата (`done`) или без точек подтверждения при рискованных шагах —
   баг: он умеет «нажимать» и не умеет «заканчивать».
8. В экосистеме `candidate` не равен `selected`: запись без проверки не считается решением, а
   `selected` с `needs_check: true` — противоречие, на котором падает CI.

Запрещено по определению (`never` в реестре): оплата и переводы, подпись документов КЭП без
человека, массовые рассылки, игра за пользователя в мультиплеере, налоговая отчётность, действия
на чужом компьютере без согласия, клонирование чужого голоса.

| M4.7 покрытие | `PROFILE-STRATEGY.md`, `APP-COVERAGE.md`, конспект 31 | профили по приоритету P0…P3, авто-профили из дампов |
| M5 кодер-агент | конспект 08, 16 | операции `dev-code`, профили IDE/терминала/Git |
| M6 разбор системы | конспект 21 | операции `processes-services`, `storage-backup` |
| M7 обновления | конспект 22, `LICENSING.md` | операции `distribution`, манифест и каналы |
| M8 релиз | конспект 13 (сборка/CI), `RUNTIME.md` | `accessibility`, скриншоты, листинг Store |

Правило: **сначала данные, потом код.** Любая способность, которую этап собирается реализовать,
должна уже существовать строкой в реестре, операцией в профиле и тест-кейсом в плане проверок.

Работа идёт **по данным, а не по ощущениям**: очередь берётся из блока состояния выше — это
домены с наименьшей глубиной и приложения из каталога без профиля, в порядке приоритета P0…P3.

Пока код приложения не пишется (по решению пользователя): только исследование, реестр, профили,
каталог, конспекты. Перед крупной задачей — уточнить требования у человека; автономная работа
до команды «стоп» разрешена.

## 7. Как проверить себя перед коммитом

```bash
python3 tools/check_all.py          # всё сразу и в правильном порядке (то же, что делает CI)
python3 tools/check_all.py --check  # то же + падает, если сгенерированное не закоммичено
```

Отдельные шаги (если нужно понять, что именно сломалось):

| Команда | Что проверяет |
| --- | --- |
| `python3 tools/actions.py` | реестр: 10 полей, допустимые риск/tier/human/status |
| `python3 tools/profiles.py` | профили: ссылки на реестр, риск не занижен, `verify` есть |
| `python3 tools/audit_actions.py` | покрытие, семейства, домены без профиля |
| `python3 tools/app_targets.py` | каталог приложений + инвариант tier A ⇒ профиль |
| `python3 tools/evals.py` | тест-план на каждое действие |
| `python3 tools/skills.py` | скиллы: реальные строки реестра, риск, критерии «готово» |
| `python3 tools/hands.py` | инструменты `data/tools.json`: реальные строки реестра, допустимый риск |
| `python3 tools/flows.py` | сценарии `data/flows.json`: шаги из реальных инструментов, риск не ниже самого опасного шага |

Rust-тулчейна может не быть рядом (песочница, новая машина). Тогда `cargo fmt` в CI сам
форматирует файлы, коммитит их и валит сборку с просьбой сделать `git pull --rebase`.
Правило, по которому это происходит: у вызова больше 60 символов аргументов — каждый
аргумент на своей строке, иначе форматирование переедет на следующем прогоне.
| `python3 tools/build_ecosystem.py` + `ecosystem.py` | 10 каталогов: свежесть, уникальные id, ≥200, честные статусы |
| `python3 tools/status.py [--check]` | блок состояния в этом файле |
| `python3 tools/dashboard.py [--check]` | `docs/DASHBOARD.md` (сводка) и `docs/INDEX.md` (индекс документов) |

**Обновить отчёты после правки данных:** `python3 tools/check_all.py`, затем
`git add -A && git commit -m "<что и зачем>" && git push`.
Ожидаемо: `problems: 0`, `family gaps=0`, `missing profiles: 0`, и `git diff` после прогона пуст
(если не пуст — генераторы надо запустить и закоммитить).

## 8. Мёртвые концы: не повторяй

- `anchor:имя → текст` внутри шага — валидатор считает это ссылкой на несуществующий якорь.
- Понижать риск операции «потому что она безопасная» — нельзя, только поднимать.
- Чинить ошибку профиля правкой валидатора — нельзя: ошибка обычно означает пропущенную строку реестра.
- Таблицы семейств глаголов писать в markdown — только в json, иначе не проверить.
- Цифры в документах писать руками — только генерация из данных.
- Считать `Smart OK` доказательством здоровья SSD, а `Build succeeded` без запуска — доказательством работоспособности.

## 9. Глоссарий

| Термин | Значение |
| --- | --- |
| Действие | строка реестра: домен + глагол + объект, с риском и tier |
| Операция | конкретный шаг в профиле, ссылающийся на действие и имеющий проверку |
| Профиль | набор операций для одного приложения/утилиты/класса работы |
| `kind` | тип профиля: `app`, `tool`, `system` |
| Tier A/B/C | A — ручной профиль (95–99 %), B — авто-профиль по UIA (80–95 %), C — визуальный агент (60–85 %) |
| Глубина домена | операции профилей / действия реестра; показывает, где обещано больше, чем сделано |
| Домен | класс способностей (`files`, `network`, `music-production`, …) |
| Семейство | тип действия (осмотр, изменение, проверка…), нужно для сбалансированности домена |
| Скилл | сценарий, собирающий операции в работу (пока не реализован) |

## 10. Если ты модель без контекста — делай так

1. Прочитай раздел 2 (маршрут) и блок состояния.
2. Если задача — **писать приложение**, открой [`docs/BUILD-GUIDE.md`](docs/BUILD-GUIDE.md): там
   контракты, архитектура, порядок этапов и критерии готовности. Дальше работай по нему.
   Если задача — **данные**, бери одну: самый мелкий домен из очереди или приложение P0/P1 без профиля.
3. Найди, как оно уже делается у соседей: `docs/PROFILES.md` → похожий профиль.
4. Добавь данные по рецептам раздела 4, прогони раздел 7, закоммить с внятным сообщением.
5. Обнови `docs/ROADMAP.md`, если закрыл пункт; конспект в `research/notes/` — если появилось
   новое знание, а не просто новая строка данных.

Не переписывай решения из `DECISION-STACK.md`, `LICENSING.md`, `RUNTIME.md` без явного указания
человека: это зафиксированные договорённости, а не черновики.
