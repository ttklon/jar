# BUILD-GUIDE: как построить ZShelper по этому репозиторию

> **Для кого этот файл.** Для модели (или человека) без контекста, которая открыла репозиторий и
> должна **написать приложение**, а не продолжать собирать каталоги. Здесь: что строим, из каких
> данных, в каком порядке, какие контракты нельзя менять, как проверять и когда считать готовым.
>
> **Как читать.** Сначала §1–§5 (30 минут), затем §6–§8 (контракты и ядро — это скелет), дальше
> по мере надобности. §19 — план по этапам, с него начинается каждый рабочий день. §22 — готовые
> промпты, их можно копировать в код как есть.
>
> **Что считается источником истины.** Не этот файл. Источник истины — данные:
> `data/actions.psv` (что умеем), `data/profiles/*.json` (как в программе), `data/skills/*.json`
> (как из этого получается работа), `data/ecosystem/*.json` (что есть снаружи),
> `data/evals.json` (как проверяем), `docs/ROADMAP.md` (когда). Если этот файл разошёлся с
> данными — правы данные, а файл надо поправить.

## 0. Правила работы над приложением

1. **Сначала данные, потом код.** Любая способность уже описана строкой реестра, профилем или
   скиллом. Код не «придумывает» новую функциональность — он **исполняет** описанное. Если
   функциональности нет в данных, сначала появляется строка/профиль/скилл (см. `AGENTS.md` §4).
2. **Ни одна операция не считается выполненной без проверки.** В данных у каждой операции есть
   `verify`. В коде это `StepResult.evidence` — доказательство из независимого источника.
3. **Риск не понижается.** Риск в реестре — минимальный; профиль и код могут только повысить его.
   Политика (§7) — единственное место, где решается «спрашивать или нет».
4. **Всё локально по умолчанию.** Никакой телеметрии, никаких «облачных улучшений», сеть — только
   по явной необходимости и по allowlist доменов.
5. **Деньги, подпись, чужие аккаунты — не наши операции.** Это `never` в реестре и `refuse` в
   скиллах. Код обязан физически не иметь пути, который это делает.
6. **Каждый коммит оставляет зелёный CI.** Генераторы (`tools/*.py`) прогоняются перед коммитом;
   сгенерированные файлы коммитятся.
7. **Не переписывать чужие слои.** Профиль приложения не правится «под удобство кода»; если код
   не может выполнить профиль — это баг кода или профиля, и он решается явно.

## 1. Что строим

**ZShelper** — автономный локальный ассистент для Windows 10/11. Обычное десктопное приложение
(не браузерная вкладка): нативное окно, трей, автозапуск, офлайн-модели, голос и текст, управление
компьютером: файлы, документы, медиа, код, музыка, сеть, устройства, умный дом.

**Три режима работы, все обязательны:**

| Режим | Что происходит | Пример |
| --- | --- | --- |
| Диалог | ответ без действий, с источниками при необходимости | «что такое EVPN» |
| Задача | план из шагов, подтверждения, выполнение, проверка | «разбери загрузки» |
| Фон | расписания, события, наблюдение | «следи за ценой и скажи, когда упадёт» |

**Чего приложение не делает** (и не должно уметь даже технически): оплата и переводы, подпись
документов КЭП, массовые рассылки, игра за пользователя в мультиплеере, налоговая отчётность,
действия на чужом компьютере без согласия, клонирование чужого голоса.

**Критерий продукта:** 15 типовых голосовых задач выполняются без ручного вмешательства, а
необратимые действия не происходят без подтверждения.

## 3. Источники истины и как их читать из кода

Пять слоёв. Каждый — файлы в репозитории; приложение читает их **в рантайме** (или встраивает при
сборке), а не дублирует в коде.

| Слой | Файл | Что даёт рантайму |
| --- | --- | --- |
| Реестр | `data/actions.json` | каталог инструментов: id, глагол, объект, риск, tier, статус |
| Профили | `data/profiles/*.json` | для приложения: якоря, шаги, проверки, поведение при сбое |
| Скиллы | `data/skills/*.json` | готовые рецепты: фразы, шаги, критерии «готово», отказы |
| Экосистема | `data/ecosystem/*.json` | что подключить снаружи (MCP, модели, коннекторы) + лицензии |
| Проверки | `data/evals.json` | сценарий на каждое действие и 15 обязательных ручных |
| Каталог приложений | `data/app_targets.psv` | какие программы обязаны работать и каким каналом |
| Политика | `data/domain_profile_policy.json` | почему у домена нет профиля (для честного «не умею») |

### 3.1 Загрузка реестра

```rust
// src-tauri/src/registry.rs
#[derive(Debug, Clone, Deserialize)]
pub struct Action {
    pub id: String,            // "files-001" — слаг, стабильный в рамках реестра
    pub domain: String,        // "files"
    pub verb: String,          // "создать"
    pub object: String,        // "папку"
    pub example: String,       // "создай папку Проект X на рабочем столе"
    pub implementation: Vec<String>, // ["fs.mkdir", "PowerShell New-Item"] — каналы
    pub risk: Risk,            // read | write-local | external | destructive | identity | money
    pub tier: Tier,            // T0..T3 (сколько ресурсов нужно)
    pub human: String,         // «может» | «редко» | «не может» — как сказано человеку
    pub human_code: Human,     // c | h | n — машиночитаемо
    pub status: Status,        // v1 | v2 | later | never
    pub notes: String,
}

impl Action {
    /// Ключ, которым ссылаются профили и скиллы: "domain|verb|object".
    /// Именно эта строка лежит в `registry` у операций профиля и в `actions[]` у шага скилла.
    pub fn key(&self) -> String {
        format!("{}|{}|{}", self.domain, self.verb, self.object)
    }
}

pub fn load_actions() -> Vec<Action> {
    // include_str! при сборке: реестр неизменен в рамках релиза
    let raw = include_str!("../../data/actions.json");
    serde_json::from_str(raw).expect("actions.json обязан быть валидным (CI)")
}
```

Профили и скиллы **не встраивать целиком**: их 87 + 20 файлов, они обновляются сервером обновлений.
Класть в ресурсы пакета (`resources/profiles/`), читать лениво по требованию.

### 3.2 Правила чтения

* `actions.json` — плоский список; индекс по `id` и по `(domain, verb)` строится на старте (< 5 мс).
* Профиль ищется по `exe` процесса: `data/app_targets.psv` → `exe` → `data/profiles/*.json[].exe`.
* Скилл ищется по фразе: BM25 по `phrases` + эмбеддинги; порог — настраиваемый.
* `status: never` → действие не попадает в каталог инструментов вообще (не «заблокировано», а
  отсутствует). Это защита от «уговорить модель».
* `tier` выше профиля железа → действие показывается, но помечается «меднo/не рекомендуется».

## 4. Архитектура

```
┌────────────────────────────────────────────────────────────────────┐
│ UI (React 19 + Fluent UI)                                          │
│  лента · план до старта · подтверждения · настройки · трей · хоткеи │
└───────────────▲───────────────────────────────┬────────────────────┘
                │ события (tauri event)         │ команды (invoke)
┌───────────────┴───────────────────────────────▼────────────────────┐
│ Rust-ядро                                                          │
│                                                                    │
│  orchestrator ── plan ── executor ── verifier ── policy            │
│      │            │         │           │          │               │
│      │            │         │           │          └─ риск, never,  │
│      │            │         │           │             подтверждения│
│      │            │         │           └─ доказательства шага      │
│      │            │         └─ каналы: cli/fs/http/com/uia/vision/mcp│
│      │            └─ LLM planner (llama-server, JSON-схема)         │
│      └─ retrieval: реестр, профили, скиллы, память                  │
│                                                                    │
│  voice (VAD/ASR/TTS) · models (download/LRU/health) · memory (SQLite)│
│  mcp (client/server) · skills (runtime) · updater · license         │
└────────────────────────────────────────────────────────────────────┘
                │                                   │
         llama-server (127.0.0.1)            MCP-серверы (stdio/http)
```

**Поток задачи (обязательный порядок):**

1. **Вход**: текст/голос/событие → нормализация → «намерение» (intent) + слоты.
2. **Поиск**: скилл по фразе → если есть, рецепт становится каркасом плана; иначе retrieval
   инструментов (5–15 карточек) по домену/глаголу/эмбеддингам.
3. **План**: LLM строит `Plan` по JSON-схеме (§6.3), каждый шаг обязан ссылаться на ключ реестра
   из реестра. План показывается человеку **до** выполнения (кроме режима «тихо», см. §13).
4. **Политика**: для каждого шага — риск, нужен ли подтверждающий токен, есть ли запрет (`never`).
5. **Выполнение**: по шагам; каждый шаг → `StepResult { ok, evidence, artifacts, error }`.
6. **Проверка**: `verifier` сверяет evidence с `verify` операции профиля/скилла. Не сошлось — шаг
   провален, план останавливается (fail-closed), пользователю показывается, что именно не так.
7. **Итог**: результат + артефакты + след (trace) в память. Скилл получает отметку «сработал».

## 6. Контракты данных (не менять без версии)

Все структуры, ходящие между слоями, версионируются полем `v`. Ломающее изменение = новая версия
и миграция.

### 6.1 Action (из реестра)

```json
{ "id": "files-001", "domain": "files", "verb": "создать", "object": "папку",
  "example": "создай папку Проект X на рабочем столе",
  "implementation": ["fs.mkdir", "PowerShell New-Item"],
  "risk": "write-local", "tier": "T0", "human": "может", "human_code": "c",
  "status": "v1", "notes": "позиция иконки на десктопе — отдельной операцией" }
```

**Два ключа, не путать.** `id` (`files-001`) — идентификатор строки. Профили и скиллы ссылаются на
действие строкой `domain|verb|object` (`files|создать|папку`) — она человекочитаема и не меняется
при перенумерации реестра. Загрузчик строит обе карты: по `id` и по `key()`.

### 6.2 Skill (из `data/skills/*.json`, урезано)

```json
{ "id": "file-sortout", "title": "Разобрать завалы в папке",
  "phrases": ["разбери загрузки", "наведи порядок в папке"],
  "scope": "инвентаризация → дубли → правила → сортировка → удаление по списку",
  "inputs": ["папка (по умолчанию Загрузки)", "правила сортировки", "порог «не трогать»"],
  "outputs": ["дерево папок", "лог перемещений", "отчёт: файлов / дублей / освобождено"],
  "domains": ["files"], "profiles": ["explorer", "everything", "7zip"],
  "time": "10–30 мин", "risk": "destructive",
  "steps": [ { "step": "Инвентаризация",
               "actions": ["files|проверить|размеры и место"],
               "verify": "число файлов, объём, топ-5 типов и диапазон дат названы числами" } ],
  "done": ["свободного места ≥ порога", "лог перемещений существует"],
  "checkpoints": ["удаление файлов вне temp/корзины"],
  "refuse": ["не удалять личные файлы без списка на подтверждение"] }
```

`actions[]` шага — **ключи реестра** (`domain|verb|object`), не `id`. Валидатор `tools/skills.py`
разрешает их в строки реестра и падает, если ключа нет или риск скилла ниже риска действия.

### 6.3 Plan — центральная структура

```json
{
  "v": 1,
  "plan_id": "01J...ULID",
  "skill_id": "system-tuneup",          // null, если план собран без скилла
  "intent": "привести систему в порядок",
  "risk": "destructive",                 // максимум по шагам
  "steps": [
    {
      "n": 1,
      "title": "Снять состояние до",
      "registry": "processes-services|показать|топ по нагрузке",
      "tool": "cli",
      "args": { "program": "powershell.exe",
                "argv": ["-NoProfile","-Command","Get-Process | Sort CPU -Desc | Select -First 5"] },
      "verify": "в выводе 5 процессов с CPU и RAM",
      "timeout_ms": 15000,
      "needs_confirmation": false,
      "reversible": true
    }
  ],
  "budget": { "steps": 12, "seconds": 600, "tokens": 12000 },
  "created_by": "planner:qwen3-8b"
}
```

**Инварианты плана (проверяются до выполнения):**
* каждый `registry` существует в реестре и его `status != never`;
* `risk` плана = максимум по шагам, не меньше риска скилла;
* шаг с `risk in {destructive, external, identity, money}` обязан иметь `needs_confirmation: true`;
* сумма `budget.seconds` ≥ суммы таймаутов шагов;
* шагов не больше `budget.steps`.

### 6.4 StepResult


## 7. Политика риска и подтверждения (`policy.rs`)

**Единственное место**, где решается, можно ли выполнять шаг. Ни UI, ни планировщик не имеют права
обойти эту функцию.

```rust
pub enum Decision { Allow, AllowWithNotice, AskUser(Token), Deny(&'static str) }

pub fn decide(step: &Step, ctx: &Context) -> Decision {
    if step.action().status == Status::Never { return Deny("never в реестре"); }
    if step.args().touches_money_or_identity() { return Deny("деньги и подпись — только человек"); }
    match step.risk() {
        Risk::Read => Allow,
        Risk::WriteLocal => if ctx.has_undo(step) { AllowWithNotice } else { AskUser(Token::new(step)) },
        Risk::External => AskUser(Token::new(step)),
        Risk::Destructive | Risk::Identity | Risk::Money => AskUser(Token::new(step)),
    }
}
```

**Правила:**
* Подтверждение — **одноразовый токен** с привязкой к `plan_id + step.n + args_hash`; изменились
  аргументы — токен недействителен.
* Подтверждение показывает: что именно будет сделано, какие пути/адреса затронуты, что будет
  удалено, можно ли откатить.
* «Подтвердить всё» разрешено только для плана, где все шаги `write-local` и обратимы.
* `destructive` без возможности отката — подтверждение **всегда**, даже в «тихом» режиме.
* Не более одного подтверждения на шаг; повторный запрос — баг.
* Каждый отказ и каждое подтверждение пишутся в `audit` (локально).

**Never-лист** (жёстко в коде, не в данных): оплата, перевод, подпись КЭП, массовая рассылка,
вход в чужой аккаунт, отключение защиты Windows, изменение чужих файлов вне рабочей папки без
подтверждения.

## 8. Исполнитель и каналы (`executor/`)

Один шаг = один вызов канала. Канал возвращает `StepResult`, никогда не «кидает» наружу.

### 8.1 CLI-канал — главный, даёт ~60 % реестра

Без него нет ничего. Требования:

```rust
pub struct CliSpec { program: String, argv: Vec<String>, cwd: Option<PathBuf>, env: Vec<(String,String)>, stdin: Option<String>, timeout_ms: u64 }

pub fn run_cli(spec: &CliSpec) -> StepResult {
    // 1) собрать команду БЕЗ shell-строки: только program + argv (никаких cmd /c "…")
    // 2) process group = Job Object, чтобы убить всё дерево по таймауту/отмене
    // 3) stdout/stderr — читать параллельно, кольцевой буфер (последние 256 КБ)
    // 4) кодировка: UTF-8 → OEM (cp866) → UTF-16LE (автоопределение)
    // 5) вернуть exit_code, stdout_tail, stderr_tail, duration
}
```

**Правила:**
* `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -Command …` — только с
  аргументами-массивами; никогда не собирать строку из пользовательских данных без экранирования.
  Пользовательский текст передаётся через stdin или переменную окружения, не через конкатенацию.
* Долгие команды (> 20 с) — с прогрессом в UI и возможностью отмены.
* Вывод больше 2 МБ — в артефакт-файл, в evidence — путь + hash.
* Требуются права администратора → шаг помечается `needs_elevation`, спрашивается отдельно и
  выполняется через отдельный процесс с UAC-манифестом (`runas`), результат возвращается по файлу.

**Опорные команды** (проверить каждую на живой Windows, сохранить в `tests/fixtures/cli/`):
`Get-Process`, `Get-Service`, `Get-Volume`, `Get-NetAdapter`, `Get-NetTCPConnection`,
`Get-CimInstance Win32_*`, `Get-WinEvent`, `Get-ScheduledTask`, `Get-AppxPackage`,
`Set-Volume`, `Clear-RecycleBin`, `Get-ChildItem`, `Compress-Archive`, `Expand-Archive`,
`Get-FileHash`, `winget list|install|upgrade`, `powercfg /batteryreport`, `ipconfig /flushdns`,
`netsh wlan show interfaces`, `robocopy`, `ffmpeg`.

### 8.2 FS-канал

* Все операции — через `tokio::fs` + `walkdir`; симлинки не разыменовывать по умолчанию.
* Удаление: сначала «в корзину» (`IFileOperation`/`SHFileOperation`), только при явном
  «удалить безвозвратно» — `std::fs::remove`. Список удаляемого показывается заранее.
* Перезапись существующего файла — всегда с бэкапом `*.zsbak` рядом (LRU, 7 дней).
* Пути: длинные (`\\?\`), Юникод, пробелы — тестировать отдельно.

### 8.3 HTTP-канал

* Только `https`, allowlist доменов на домен задачи (`web`: список в настройках).
* Никаких автоматических редиректов на другой хост; cookie не сохранять по умолчанию.
* Юзер-агент честный: `ZShelper/<version>`.
* Лимит: 5 МБ ответа, 15 с таймаут, 3 попытки с backoff.
* Для чтения страниц — отдельный «ридер» (readability → markdown), без исполнения JS.

### 8.4 COM-канал (Office, 1С)

* `windows` crate: `CoInitializeEx(APARTMENTTHREADED)`, `IDispatch` через `windows::core::Interface`.
* Проверка: приложение запущено (по `Process` + `GetActiveObject`).
* Word/Excel/Outlook/OneNote: открыть → сделать → **сохранить новый файл**, не перезаписывать
  оригинал без подтверждения.
* Outlook: только создание черновика; отправка — `never`.
* 1С: подключение к базе в режиме «обычное приложение» через COM, только чтение или создание
  документов по шаблону, никогда не проведение документов без человека.

### 8.5 UIA-канал (fallback для программ без CLI/API)

```
1) найти окно по процессу/заголовку (UIA tree walk с ограничением глубины 12)
2) элемент — по ControlType + Name + AutomationId + индекс; правило "первый совпавший"
3) действие — Invoke, Value.SetValue, SelectionItem.Select, Toggle
4) после действия ОБЯЗАТЕЛЬНО перечитать состояние элемента/окна (evidence: uia_state)
5) если элемент не найден за 3 с — vision-канал (screenshot + OCR), но клик по координатам
   разрешён только при подтверждении "клик по найденному тексту"
```

Ограничения: UIA медленный (10–100 мс на элемент), поэтому профили приложений кэшируют «путь» до
элемента (AutomationId цепочкой) и проверяют его валидность перед использованием.

### 8.6 Vision-канал

* Скриншот активного окна (`Windows.Graphics.Capture` или `BitBlt` fallback).
* OCR — Windows OCR (`Windows.Media.Ocr`) для текста, VLM — для «где кнопка».
* Никаких кликов «на глаз» без подтверждения; координаты проверяются повторным скриншотом
  (элемент всё ещё там?).
* Данные экрана не покидают машину.

## 9. Модели и инференс

### 9.1 Роли моделей

| Роль | Что делает | Требования | Кандидат по умолчанию |
| --- | --- | --- | --- |
| `router` | намерение, выбор скилла, короткие ответы | ≤ 2 ГБ, быстрый | Qwen3-1.7B / Gemma-3-1B (Q4) |
| `workhorse` | план, длинные ответы, код | 4–6 ГБ | Qwen3-8B (Q4_K_M) |
| `vlm` | экран, документы, картинки | 3–5 ГБ | Qwen2.5-VL-7B / MiniCPM-V (Q4) |
| `embed` | поиск, память | ≤ 300 МБ | bge-m3 / e5-small (ONNX) |
| `asr` | речь → текст | ≤ 1 ГБ | whisper large-v3-turbo (int8) |
| `tts` | текст → речь | ≤ 500 МБ | Kokoro-82M / Piper (ru) |
| `vad` | детект речи | ≤ 5 МБ | Silero VAD |

Реализованные сейчас роли (`router`, `workhorse`, `embed`) описаны данными в
`data/roles.json`: идентификатор, назначение и потолок размера. Привязка идёт от роли к
файлу на диске и проверяется по размеру — ссылок и эталонных хешей там нет намеренно.

Конкретные файлы, sha256 и лицензии — из `data/ecosystem/models.json` (поле `selected` = проверено;
`candidate` = требует проверки лицензии перед включением в сборку).

### 9.2 Менеджер моделей

```rust
pub struct ModelManager { root: PathBuf, manifest: Manifest, running: Mutex<HashMap<Role, ServerHandle>> }

impl ModelManager {
    pub fn ensure(&self, role: Role) -> Result<Ready>;   // скачать при необходимости + запустить
    pub fn download(&self, id: &str) -> impl Stream<Item = Progress>; // resume + sha256 + atomic rename
    pub fn evict_lru(&self, need_bytes: u64);            // удалять только неактивные, спрашивать при > 2 ГБ
    pub fn health(&self) -> Vec<RoleHealth>;             // /health, время ответа, VRAM
}
```

Правила:
* Скачивание: `.part` → проверка `sha256` → атомарное переименование. Не сошлось — удалить, ошибка.
* Зеркала: основной URL + 1 запасной; источник пишется в лог.
* Место на диске проверяется **до** скачивания; при нехватке — предложить освободить/удалить LRU.
* `llama-server` запускается на `127.0.0.1:<свободный порт>`, `--no-webui`, `-c 8192`,
  `--parallel 1`, `--no-mmap` на HDD. Порт и PID — в состоянии; при падении — перезапуск (3 попытки).
* Один `workhorse` одновременно; `router` может жить параллельно. VRAM: не более 80 % доступной.
* Не тянуть модель на батарее (настройка «не скачивать при питании от батареи»).

**Состояние на сейчас:** папка моделей, чтение заголовка GGUF, сверка sha256, скачивание
через `curl`, место на диске и удаление — сделаны. Процесс-менеджер (`server.rs`) проверен
на заглушке (`HttpListener`): запуск, ожидание `/health`, таймаут, остановка. `llama-server`
подключён (`llama.rs`): поиск бинарника, флаги, запуск и остановка с экрана «Модели»,
остановка при выходе. **Что не проверено:** сам бинарник в сборке не поставляется и в CI не
запускался — проверены флаги, поиск и весь путь «процесс + /health» на заглушке, но не
реальная загрузка весов на живой видеокарте.

### 9.3 Промпт-контракт с моделью

* Всегда: JSON-схема (грамматика GBNF от llama.cpp или `response_format json_schema`), температура
  0.1–0.3 для плана, 0.7 для диалога.
* Всегда: `max_tokens` по роли; обрыв по лимиту = ошибка плана, а не «частичный план».
* Ретраи: 2 попытки с сообщением «твой JSON не прошёл валидацию: <ошибка>».
* Контекст: карточки инструментов (≤ 15), релевантные факты (≤ 10), история (≤ 6 реплик). Не
  вставлять весь реестр — только выбранное retrieval.

## 10. Голос

Конвейер: **микрофон → VAD → сегмент → ASR → текст → (тот же путь, что текст) → TTS → динамик**.

* Захват: `cpal` WASAPI, 16 кГц моно, кольцевой буфер 5 с.
* VAD: Silero (ONNX), порог 0.5, «конец фразы» — 500 мс тишины; barge-in: говорим — TTS
  останавливается.
* ASR: `whisper-cli` как sidecar (stdin wav → stdout json), модель `large-v3-turbo int8`;
  fallback — Windows Speech Recognition (хуже, но работает).
* TTS: Kokoro (ru-голос) через ONNX; fallback — SAPI (`ISpVoice`, голос «Ирина»).
* Wake-word: openWakeWord, своё слово («Зет», «Помощник») — тренируется отдельно, по умолчанию
  выключено (жрёт CPU).
* Горячая клавиша `Ctrl+Alt+Z` — push-to-talk: пока держишь, слушаем; отпустил — распознаём.

Требования: полный цикл «сказал → ответил» ≤ 3 с на железе 16 ГБ / CPU; индикатор записи всегда
виден; звук никогда не пишется на диск без явного «сохрани запись».

## 11. Память

SQLite (`%LOCALAPPDATA%\ZShelper\memory.db`), WAL. Миграции — `refinery` или ручные `user_version`.

```sql
-- эпизоды: что просили и что вышло
CREATE TABLE traces(id TEXT PRIMARY KEY, started_at INTEGER, plan_id TEXT, phrase TEXT,
                    outcome TEXT, risk TEXT, skill_id TEXT, cost_ms INTEGER, model TEXT);
CREATE TABLE steps(trace_id TEXT, n INTEGER, registry TEXT, ok INTEGER, error TEXT,
                   evidence_kind TEXT, PRIMARY KEY(trace_id,n));
-- факты: устойчивые знания о пользователе
CREATE TABLE facts(id TEXT PRIMARY KEY, subject TEXT, predicate TEXT, object TEXT,
                   confidence REAL, source_trace TEXT, created_at INTEGER, expires_at INTEGER);
-- артефакты и файлы
CREATE TABLE artifacts(path TEXT PRIMARY KEY, kind TEXT, bytes INTEGER, sha256 TEXT, trace_id TEXT);
CREATE VIRTUAL TABLE files_fts USING fts5(path, name, content='files');
-- векторы (эмбеддинги) — BLOB float32, косинус в Rust; при > 50k — sqlite-vec
CREATE TABLE vectors(ref_id TEXT, ref_kind TEXT, vec BLOB);
```

Правила:
* Факт с `confidence < 0.6` не используется как основание для действия, только как подсказка.
* Предпочтения («музыка тихо», «файлы в D:\Docs») записываются только по явному подтверждению.
* «Забудь это» — реальное удаление строки + из векторов.
* Содержимое файлов не индексируется целиком без разрешения; имя + путь + метаданные — можно.
* Экспорт/импорт памяти — JSON, по кнопке. Никуда не отправляется.

## 12. Скиллы в рантайме

Скилл — не «промпт», а **фиксированный каркас** с параметрами.

1. Матчинг: `phrases` (BM25) + эмбеддинг фразы + домен из намерения. Порог: 0.62 BM25-score или
   0.80 cosine; ниже — обычный планировщик.
2. Если скилл найден: его шаги становятся **обязательным каркасом**, LLM только заполняет
   параметры (пути, имена, пороги) и может добавить шаги между ними, но не удалять.
3. `verify` каждого шага скилла — критерий приёмки этого шага (см. §6.4).
4. `checkpoints` — где обязательно спросить человека, даже если риск низкий.
5. `refuse` — что скилл не делает ни при каких формулировках.
6. Успех: все шаги ok + `done` выполнено. Иначе — `partial` и честный отчёт.

**Автообучение (осторожно):** если задача решена без скилла и повторяется ≥ 3 раза с одинаковым
каркасом — предложить пользователю «сохранить как скилл» (черновик в `data/skills/_drafts/`,
никогда не активируется автоматически).

## 14. MCP

* Клиент: JSON-RPC 2.0, транспорт stdio (spawn процесса) и Streamable HTTP.
* `initialize` → `tools/list` → кэш карточек (TTL 1 ч, инвалидация по изменению процесса).
* Каждый MCP-инструмент получает **риск-класс** из политики (по имени/описанию + ручной override в
  `data/ecosystem/mcp-servers.json`); без класса — `external` по умолчанию, то есть подтверждение.
* Аргументы валидируются JSON-схемой сервера **до** вызова.
* Таймаут 30 с; отмена — убить процесс (stdio) или оборвать поток (HTTP).
* Серверы из экосистемы: только `selected` попадают в список «рекомендуемые»; `candidate` — в
  «требует проверки» с указанием, что именно не проверено (лицензия/канал/запуск).
* Свой MCP-сервер (обратная сторона): отдавать наружу только `read`-инструменты и «предложить
  план», никогда — исполнение.

## 15. Секреты и безопасность

* Секреты (токены, пароли, ключи) — **только** DPAPI (`CryptProtectData`, scope = user) в
  `%LOCALAPPDATA%\ZShelper\secrets.bin`. В коде, логах, памяти — никогда в открытом виде.
* Логи не содержат: содержимого файлов, URL с токенами, путей к личным документам (маскируются до
  `<home>\…\file.ext`).
* Сетевые вызовы — через один `HttpClient` с allowlist; каждое новое доменное имя — запись в audit.
* Процессы: запуск без shell, с Job Object, с ограничением по памяти (`JOBOBJECT_EXTENDED_LIMIT`),
  чтобы «зависший ffmpeg» не съел машину.
* UI Automation и скриншоты не работают, если окно защищено (banking) — это должно быть явной
  ошибкой, а не «пустым скриншотом».
* Автообновление: подпись манифеста, проверка версии и хеша, откат на предыдущую при старте
  «не поднялось 2 раза».
* Capability-манифест Tauri — минимальный: никакого `shell:allow-execute` общего вида; только
  собственные команды ядра.

## 17. Производительность и бюджеты

| Метрика | Цель | Как мерить |
| --- | --- | --- |
| Холодный старт до готовности UI | ≤ 2.5 с | ETW/логи `main.rs` |
| Готовность к задаче (модель загружена) | ≤ 8 с | время до первого ответа `router` |
| Ответ диалога первый токен | ≤ 1.2 с | llama-server metrics |
| План простой задачи | ≤ 4 с | trace |
| Голос: конец фразы → начало ответа | ≤ 3 с (CPU), ≤ 1.5 с (GPU) | trace |
| Память процесса в покое | ≤ 350 МБ (без моделей) | Task Manager |
| Диск: приложение + сайдкары | ≤ 400 МБ (модели отдельно) | `du` |
| CPU в покое | ≤ 1 % | Task Manager 10 мин |

Правила: ничего не грузить «на всякий случай»; модели — по требованию; превью/индексы — в фоне с
низким приоритетом (`SetThreadPriority(BELOW_NORMAL)`); при питании от батареи тяжёлое не начинать.

## 18. Сборка, CI и релиз

### 18.1 Локально

```powershell
npm ci                              # фронтенд-зависимости (lock-файл в репозитории)
npm run dev                         # UI в браузере на данных из репозитория — без Rust
npm run tauri dev                   # приложение целиком (нужен Rust + WebView2)
npm test                            # инварианты реестра + дымовые тесты UI
cargo test --manifest-path src-tauri/Cargo.toml   # тесты ядра (реестр встроен в бинарник)
python tools/check_all.py           # данные (обязательно перед коммитом)
```

Что уже стоит в репозитории на момент написания (проверять, а не предполагать):
`src-tauri/src/{registry,policy,tools,flows,profiles,memory,planner,models,download,server,llama,roles,ipc,tray,logging,lib}.rs`,
`src/{app,screens,components,ipc,lib,i18n}`, `scripts/make_icons.py`, джобы `ui`, `core` и `release`
в `.github/workflows/app.yml`.

### 18.2 CI (`.github/workflows/`)

| Job | Что делает | Когда |
| --- | --- | --- |
| `validate` | python-генераторы + `--check` (реестр, профили, скиллы, экосистема, dashboard, ссылки) | каждый push |
| `ui` | `npm run typecheck` + `npm test` + `npm run build` | каждый push |
| `core` | на Windows: `cargo clippy -D warnings`, `cargo test`, `cargo fmt --check` | каждый push |
| `package` | `tauri build` (NSIS) + MSIX через MakeAppx, подпись (секреты), артефакт | тег `v*` |
| `audit` | `cargo deny`, `npm audit`, SBOM | раз в неделю |

Правило: **сгенерированные файлы коммитятся**; `--check` падает на расхождении. Это защита от
«в данных одно, в документах другое».

### 18.3 Релиз

1. Версия: `0.x.y` до v1; changelog из коммитов (`git cliff` или руками).
2. Сборка: `tauri build` даёт NSIS-установщик. **MSIX Tauri сам не собирает** —
   `bundle.targets` принимает `nsis`/`msi`, а попытка указать `msix` валит
   `build.rs` (`data did not match any variant of untagged enum BundleTargetInner`).
   MSIX делается отдельным шагом: `MakeAppx pack` + `AppxManifest.xml`, затем
   `signtool sign`, `signtool verify /pa`, проверка на чистой ВМ без Visual Studio.
3. Обновление: манифест `latest.json` (stable/beta), sha256, размер; клиент проверяет подпись.
4. Откат: предыдущий MSIX хранится; «не поднялось» → откат автоматически, лог пользователю.
5. Телеметрии нет — качество релиза оценивается по добровольным отчётам и нашим прогонам evals.

## 20. Антипаттерны (почему проекты такого класса умирают)

| Антипаттерн | Чем плохо | Как правильно |
| --- | --- | --- |
| «Сначала красивый UI, потом логика» | UI фиксирует неверные контракты | сначала домен и IPC, UI — обёртка |
| Планировщик без валидации ключей реестра | модель «изобретает» возможности | схема + проверка по реестру + отказ |
| Успех по `exit_code == 0` | ложные «готово» | независимый evidence |
| Клики по координатам как основа | хрупко, опасно | UIA/AutomationId, vision — только fallback с подтверждением |
| Один мегапромпт на всё | нестабильно, дорого | роли моделей + каркасы скиллов |
| Своя БД «на будущее» | вес и сложность | SQLite, пока не упрётся |
| Телеметрия «для улучшения» | недоверие, приватность | ноль телеметрии |
| Обход политики «для удобства тестов» | дыра в безопасности | тестовый режим — флаг сборки, не рантайма |
| Автообновление без отката | кирпичи у пользователей | 2 попытки → откат |
| Скиллы, сгенерированные моделью, включаются сами | непредсказуемость | только черновики + подтверждение |

## 22. Готовые промпты (копировать в код как есть)

### 22.1 Router — намерение и выбор скилла

```
Ты — маршрутизатор локального ассистента Windows. Ничего не выполняй.
Верни JSON по схеме.

Вход: фраза пользователя, список скиллов (id + title + phrases), список доменов.
Выход:
{"intent":"chat|task|schedule","skill_id":string|null,"domains":[string],"confidence":0..1,
 "slots":{...},"need_clarify":string|null}

Правила:
- skill_id только из переданного списка; если сомневаешься — null.
- confidence < 0.5 → need_clarify с одним коротким вопросом.
- Никогда не выдумывай домены вне списка.
```

### 22.2 Planner — построение плана

```
Ты — планировщик локального ассистента Windows. Ты НЕ выполняешь действия, только планируешь.

Тебе даны:
1) карточки инструментов (ключ реестра, домен, глагол, объект, пример, риск, каналы);
2) каркас скилла (если есть) — его шаги обязательны;
3) факты о пользователе (пути, предпочтения) — только те, что даны.

Верни план по схеме v1 (см. §6.3). Жёсткие правила:
- каждый шаг обязан содержать registry ИЗ ПЕРЕДАННЫХ карточек;
- если для шага нет подходящего ключа — верни {"error":"не умею: <чего именно>"};
- destructive/external/identity — needs_confirmation=true;
- не больше {budget.steps} шагов; предпочитай меньше шагов при том же результате;
- каждый шаг должен иметь verify — как проверить результат независимо;
- не придумывай пути: используй fact-пути, иначе спроси (need_input).
```

### 22.3 Verifier — проверка шага

```
Ты проверяешь, выполнен ли шаг. Тебе даны: цель шага, критерий verify, evidence (stdout/exit code/
состояние/файл), контекст. Отвечай JSON: {"ok":bool,"reason":string,"evidence_ok":bool}.

Правила:
- ok=true только если evidence ЯВНО подтверждает критерий;
- «команда завершилась без ошибок» ≠ «результат достигнут»;
- если evidence неполный — ok=false, reason="недостаточно доказательств: …";
- никогда не предполагай, что действие удалось.
```

### 22.4 Ответ пользователю

```
Ты — локальный ассистент. Отвечай по-русски, коротко и по делу.
Что сделано — только факты из evidence. Что не сделано — прямо, без смягчений.
Если что-то не проверено — так и скажи. Никаких «успешно завершено», если нет доказательств.
Не предлагай действия, которых нет в каталоге инструментов.
```

### 22.5 Сжатие контекста для длинных задач

```
Сожми историю задачи в 10 строк: цель, что уже проверено (с evidence), что осталось, какие пути
используются, какие решения приняты и почему. Сохрани все числа и пути. Ничего не выдумывай.
```
