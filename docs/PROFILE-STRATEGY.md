# Стратегия покрытия приложений: как «уметь в любом приложении» не превращается в 500 ручных профилей

Проблема, которую решает этот документ: на Windows десятки тысяч программ. Ручной профиль
(якоря + шаги + проверки) стоит 1–3 часа. 500 профилей — это полгода работы. При этом
пользователю нужно, чтобы ZShelper работал **в любой программе уже сегодня**.

Решение: три уровня покрытия. Профиль — не условие работы, а **ускорение**.

---

## 1. Три уровня

| Tier | Что | Надёжность | Скорость | Стоимость появления |
| --- | --- | --- | --- | --- |
| **A** | Ручной профиль: якоря (UIA/hotkey/OCR), шаги, обязательная проверка | 95–99 % | быстрый (0.3–2 с/шаг) | 1–3 часа на приложение |
| **B** | Авто-профиль: UIA-дамп → кандидаты якорей → подтверждение человеком | 80–95 % | быстрый | 2–5 минут на приложение |
| **C** | Визуальный агент: скриншот → OCR/VLM → клик → проверка | 60–85 % | медленный (1–3 с/шаг) | 0 (работает сразу) |

Каталог целей и текущий tier каждого приложения — [`APP-COVERAGE.md`](APP-COVERAGE.md)
(источник: `data/app_targets.psv`, 122 приложения).

**Инвариант:** приложение tier A обязано иметь профиль в `data/profiles/` — это проверяет
`tools/app_targets.py` в CI. Нет профиля — либо добавляй, либо понижай tier.

## 2. Как появляется профиль tier B (автоматически)

```
пользователь: «сделай что-то в программе X»
        │
        ├─► приложение не в каталоге? → спросить разрешение на «осмотр окна»
        │
        ├─► tools/uia_probe.py dump --exe X.exe --out dump.json
        │       снимает дерево UIA: имена, AutomationId, ControlType, IsEnabled, паттерны
        │
        ├─► tools/uia_probe.py draft --dump dump.json --out data/profile_drafts/x.json
        │       черновик: якоря из стабильных элементов, операции из меню/кнопок,
        │       тип интерфейса (UIA / Electron / Qt / игровой канвас)
        │
        ├─► агент дописывает verify (обязательно!) и risk, показывает человеку
        │
        └─► «подтверждаю» → data/profiles/x.json + verified_at → tier A
```

Практические правила для дампа:

1. **Якоря берём из стабильного:** `AutomationId` (лучше), `Name` (хуже — локализуется),
   `ControlType` + позиция в дереве (последний вариант для UIA).
2. **Игнорируем «шум»:** тултипы, скроллбары, элементы с рандомными именами (`Item 14`).
3. **Канвасные приложения** (игры, Photoshop-холст, Electron с кастомным рендером) —
   сразу tier C, не тратим время на UIA.
4. **Локализация:** если `Name` на русском, а интерфейс может быть английским — нужен
   двойной якорь (Name + горячая клавиша/меню), иначе профиль сломается у другого пользователя.

## 3. Как работает tier C (визуальный агент)

Универсальный цикл, не требующий профиля:

```
скриншот активного окна (или области)
   → OCR (текст + боксы) и/или VLM («где кнопка Экспорт?»)
   → выбор цели с проверкой: цель в фокусе? подпись совпадает?
   → клик (SendInput) с проверкой, что координата не изменилась
   → верификация результата: изменение экрана / UIA-состояния / файла
   → если не получилось 2 раза — остановка и вопрос человеку
```

Ограничения, которые нужно честно показывать пользователю:

- медленнее (1–3 с против 0.3 с);
- не работает в полноэкранных играх с анти-читом (и не должно — см. реестр `games`);
- чувствителен к масштабу экрана и теме (компенсируется OCR-якорями и мультимасштабом);
- **всегда требует подтверждения** для `destructive`/`external`: клик «наугад» по кнопке
  «Удалить» — это инцидент, а не автоматизация.

## 4. Дрейф интерфейса и переобучение

| Событие | Реакция |
| --- | --- |
| Якорь не найден | не кликать наугад; откат; сообщение «интерфейс изменился» |
| Приложение обновилось (версия exe изменилась) | пометить профиль «непроверенный», требовать подтверждения для write/destructive |
| Пользователь показал, как делает | запись UIA-траектории → новый профиль (tier B → A) |
| 3 неудачи подряд | переключение на tier C + алерт в Telegram |

Поле `verified_at` — обещание: если профилю больше 6 месяцев и приложение обновилось,
доверие к нему падает автоматически.

## 5. Порядок расширения (что делать в следующие итерации)

1. **P0 (уже есть):** Проводник, браузер, Word, Excel, CapCut, OBS, Telegram, PowerShell, cmd.
2. **P0 (следующие):** FL Studio, REAPER, Blender, 7-Zip, HandBrake, VLC, Git — по каталогу.
3. **P1:** Photoshop, Premiere, Outlook, VS Code, Discord, Steam, 1С, банк, Figma, DaVinci.
4. **P2:** LibreOffice, Acrobat, Audacity, Ableton, Bitwig, Docker, DBeaver, WinSCP, FileZilla.
5. **P3 / tier C:** игры, канвасные редакторы, узкоспециальный софт.

Правило приоритета: **сначала те приложения, где пользователь проводит часы**, а не те,
которые проще автоматизировать.

## 6. Почему это масштабируется лучше, чем «500 профилей»

- 90 % запросов укладываются в 30–40 программ — их и делаем руками (tier A);
- остальные 80+ из каталога закрываются авто-профилем за минуты (tier B);
- всё, чего нет в каталоге, работает через визуальный агент (tier C) **сразу**, без
  предварительной подготовки;
- каждый новый запрос оставляет артефакт: каталог, профиль, eval-кейс.

## 7. Проверки в CI

| Проверка | Инструмент | Что ловит |
| --- | --- | --- |
| Профиль ↔ реестр | `tools/profiles.py` | операция без строки реестра, занижение риска, отсутствие verify |
| Tier A ⇒ профиль | `tools/app_targets.py` | обещание без реализации |
| Якоря существуют | `tools/profiles.py` | шаг ссылается на несуществующий якорь |
| Каталог валиден | `tools/app_targets.py` | неизвестный канал/tier/приоритет |
| Черновики не попадают в релиз | `data/profile_drafts/` не читается валидатором | неподтверждённый профиль в проде |
