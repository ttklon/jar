# 24 — Таксономия действий: как «уметь всё» превращается в инженерный список

Требование: «продумай каждое действие, каждый шаг, всё, что человек делает в компьютере,
и всё, что человек вообще не может — программа должна уметь сама».

Прозой это не решается: список из чата теряется, дублируется и не проверяется. Поэтому
действия **сведены в машиночитаемый реестр**: [`data/actions.psv`](../data/actions.psv) →
[`data/actions.json`](../data/actions.json) → каталог [`docs/ACTIONS.md`](../docs/ACTIONS.md).

**Текущее состояние: 717 действий, 45 доменов, 184 уникальных глагола; 0 дырок по семействам.**
Пересборка: `python3 tools/actions.py`.

---

## 1. Метод: почему такой список можно считать исчерпывающим

Полнота достигается перемножением пяти измерений, а не «перечислением всего, что вспомнилось».

```
ДЕЙСТВИЕ = ОБЪЕКТ × ГЛАГОЛ × КОНТЕКСТ × МАСШТАБ × РИСК
```

| Измерение | Значения | Пример |
| --- | --- | --- |
| **Объект** | 33 класса (файл, окно, служба, календарь, видео, БД…) | `служба` |
| **Глагол** | 14 семейств (см. §2) | `остановить` |
| **Контекст** | локально / GUI / API сервиса / сеть / устройство / другая ОС | через `sc` |
| **Масштаб** | одна сущность / пачка / по расписанию / непрерывно / 24-7 | 200 служб |
| **Риск** | R / W / D / E / M / I | D (разрушительное) |

Так «уметь всё» становится **конечным и проверяемым**: 33 × 14 = 462 клетки, из которых
717 уже заполнены (некоторые клетки бессмысленны: «удалить календарь» не существует,
«создать сеть» — это настройка, а не создание).

## 4. Как реестр управляет продуктом (а не просто лежит)

```
data/actions.json
   ├──► data/evals.json       — по одному сценарию на действие (docs/EVALS.md)
   ├──► Capability Registry   — id, risk, permissions, tier, undo
   ├──► Planner tool cards    — title + whenToUse (что видит LLM)
   ├──► Policy engine         — по risk и объекту (папки, домены, службы)
   ├──► Settings «Способности» — что умеет ИМЕННО эта машина (по tier)
   ├──► Evals                 — по одному сценарию на семейство действий
   └──► Roadmap / отчёты      — сколько сделано, что в v2, что «never»
```

Правила, которые из этого следуют:
1. **Нет строки — нет фичи.** Новое умение начинается с записи в `actions.psv`, а не с кода.
2. **Риск назначается в реестре**, а не моделью в рантайме.
3. **Tier назначается в реестре** — planner не предлагает то, что не влезет в железо.
4. **`never` — это тоже решение** (игра за игрока, смена пароля, банковские операции),
   с причиной в примечании; оно показывается пользователю, чтобы не было ложных ожиданий.

## 5. Суперспособности: чего человек не может (и почему это требует инженерии, а не лозунгов)

| Суперспособность | Что даёт | Обязательное условие, иначе вред |
| --- | --- | --- |
| **Круглосуточно** | работает ночью, пока человек спит | лимиты времени/токенов/диска, heartbeat, стоп-слово, «3 ошибки → пауза» |
| **Параллельно** | 200 проверок одновременно | ограничение конкурентности, один владелец мыши/клавиатуры |
| **Без устали и ошибок** | 500 одинаковых правок | детерминизм, проверка после каждого шага, лог |
| **Идеальная память** | «что я говорил в марте» | TTL, право забыть, «покажи всё, что знаешь обо мне» |
| **Масштаб чтения** | 300 статей → вывод | бюджет контекста, map-reduce, цитаты |
| **Скорость в GUI** | 100 форм за минуту | проверки результата, иначе «слепой» ввод в пустоту |
| **Тотальная верификация** | проверяет каждый шаг | верификаторы в реестре actions (поле verify) |
| **Непрерывный мониторинг** | 1000 сигналов | пороги, анти-спам, тихие часы |
| **Саморасширение** | достаёт недостающие умения | изоляция, права, аудит (см. `20-self-extension.md`) |

Ключевая мысль: суперспособность — это **не «агент может всё»**, это «агент может то, что
человеку физически недоступно, **при наличии предохранителей**». Каждая строка реестра с
`человек = не может` обязана иметь ограничитель в реализации.

## 6. Чего в реестре намеренно нет (и где это живёт)

| Не в реестре | Где описывается |
| --- | --- |
| Кнопки внутри конкретных приложений (CapCut, Photoshop, 1С) | `profiles/<app>.json` (якоря, шаги, проверки) |
| Операции внутри веб-сервисов (Notion, Google Docs) | браузерный агент + MCP-коннектор |
| Драйверы, прошивки, промышленное оборудование | плагины/MCP по требованию |
| Действия, требующие чужих ключей | коннекторы (`12-connectors.md`) |
| Юридически значимые действия (КЭП, налоги, банк) | `never` / «навигатор» |

Это не пробелы, а **разные слои**: реестр — про *что*, профили — про *как в конкретной
программе*, MCP — про *чем*.

## 8. Как проверять полноту (аудит покрытия)

1. **CRUD-тест по каждому объекту**: для 33 классов проверить наличие create / read / update /
   delete / find / verify. Отсутствие — либо осознанное `never`, либо пробел.
2. **Тест «человеческих» сценариев**: 50 бытовых фраз («переключи звук», «сожми PDF»,
   «найди договор», «поставь встречу») — каждая должна найти строку в реестре.
3. **Тест масштаба**: для каждого семейства — есть ли вариант «пачка / по расписанию / 24-7».
4. **Тест границ**: для каждого `D`/`E`/`I` — есть ли подтверждение и откат.
5. **Тест суперспособностей**: для каждой строки `человек = не может` — есть ли ограничитель.

Эти пять проверок автоматизируются из `actions.json` — то есть полнота становится
**CI-проверкой**, а не мнением.

## 11. Открытые вопросы

- Как описывать «составные» действия (сценарии из 5 шагов) — как отдельные записи реестра
  с `steps[]` или как скиллы? Гипотеза: скиллы, реестр — только атомарные действия.
- Нужен ли `money`-класс вообще, если мы его не автоматизируем? Да, как маркировка
  «показываем, но не делаем» — иначе пользователь будет ждать, что «оплати» сработает.
- Сколько строк реально нужно для «умеет всё» с точки зрения пользователя: 436 или 100?
  Гипотеза: 95 % запросов покрывают 120–150 действий; остальное — глубина и доверие.
