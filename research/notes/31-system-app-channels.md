# 31. Системные приложения Windows: какой канал автоматизации выбирать

Конспект по одиннадцати профилям, добавленным в этой итерации (Docker Desktop, Audacity,
Everything, Диспетчер задач, Windows Terminal, PowerPoint, Notion, Obsidian, Zotero,
Ableton Live, Bitwig Studio). Задача — не «описать приложения», а вывести правило:
**для каждого класса программ есть канал, который ломается в десять раз реже остальных**.
Профиль в `data/profiles/` фиксирует этот канал и оставляет UIA как страховку.

## Почему это отдельная тема

Каталог `data/app_targets.psv` делит приложения по tier, но tier B не означает «кликай, пока не
получится». У Диспетчера задач и у Bitwig Studio формально одинаковый tier, а надёжность
различается радикально: у первого есть PowerShell и CIM, у второго — Controller API на Java.
Если строить профиль «по кнопкам» в обоих случаях, получим две хрупкие автоматизации вместо
одной хрупкой и одной надёжной.

Правило простое: **сначала ищем данные, потом — команды, и только потом — пиксели**.
Соответствие каналов надёжности уже зафиксировано в профилях порядком
`api → cli → com → web → midi → jsx → remote → uia → vision`. Ниже — чем это наполняется
для системного софта.

## Что нашлось по приложениям

| Приложение | Канал, который реально работает | Что не работает | Проверка результата |
| --- | --- | --- | --- |
| Диспетчер задач | `Get-Process`, `Get-Counter`, CIM | UIA: список пересортировывается прямо во время клика | тот же процесс виден в `Get-Process` по PID |
| Службы (`mmc.exe`) | `sc.exe query`, `Get-Service`, CIM `Win32_Service` | клики по оснастке MMC, она рисует себя сама | `Status=Running` + повторный `query` через 3 с |
| Планировщик заданий | `schtasks /XML` (экспорт/импорт), `Get-ScheduledTask` | локализованные имена папок задач | `Get-ScheduledTaskInfo` показывает `LastRunTime` |
| Windows Terminal | `wt.exe` подкоманды, `settings.json`, fragments | отправка клавиш в панель, если фокус ушёл | `pwd` в панели + наличие процесса |
| Everything | `es.exe` (консольный клиент), HTTP-сервер | UIA-поле поиска: индекс обновляется асинхронно | `File.Exists` для каждого пути |
| Docker Desktop | `docker` CLI, `compose`, `scout` | Electron-UI и трей: состояние движка не совпадает с картинкой | `docker info` + `compose ps --format json` |
| Audacity | `mod-script-pipe` (named pipe), макросы | меню «Эффект»: пункты переименовываются между версиями | пересчёт LUFS/пиков после обработки |
| PowerPoint | COM (`PowerPoint.Application`), `python-pptx` | клики по ленте, особенно в локализациях | `python-pptx` открывает файл и видит плейсхолдеры |
| Notion | HTTP API (`/v1/pages`, `/v1/blocks`) | UIA внутри Chromium: дерево почти пустое | `GET /v1/pages/{id}` |
| Obsidian | обычные `.md` файлы в папке хранилища | UIA внутри Electron | файл существует и парсится как markdown с frontmatter |
| Zotero | локальный API `127.0.0.1:23119`, `zotero.sqlite` (read-only) | UI-клики по коллекциям | `GET /items` + валидный BibTeX на выходе |
| Ableton Live | AbletonOSC / Live Object Model через User Remote Script | UIA: интерфейс нарисован OpenGL, дерева нет | `/live/song/get/num_tracks` > 0 |
| Bitwig Studio | Controller API (Java) + generic OSC | UIA: тот же OpenGL-случай | `trackCount`, уровень канала > −60 dB |
| DaVinci Resolve | Python-API (`DaVinciResolveScript`), `SetRenderSettings` + `StartRendering` | UIA: Qt-интерфейс, панели пересоздаются при смене страницы | `ffprobe` результата + число кадров против таймлайна |
| WinSCP | `winscp.com /command` или COM `Session` | UIA-диалоги мастера сессий | `pwd` в сессии + сверка хэшей на сервере |
| FileZilla | URL-подключение `filezilla.exe sftp://…` + клавиатура | UIA: панели — кастомные контролы без дерева | пустая очередь + совпадение размеров после Refresh |
| DBeaver | нативные клиенты (`psql`, `mysqldump`, `sqlite3`) под тем же соединением | UIA Qt: таблицы результатов виртуализированы | `information_schema` и `PRAGMA integrity_check` |
| Visual Studio | `msbuild` + `vstest.console` + COM `DTE2` | UIA: редактор — кастомный контрол, дерево обрезано | `Build succeeded`, `.trx`-отчёт |
| JetBrains IDE | `gradlew`, `inspect.bat` (headless), `rg` | UIA Qt | XML-отчёт инспекций, `build/test-results` |
| Wireshark | `dumpcap` + `tshark -z` | UIA: список пакетов виртуализирован, прокрутка ломает индексы | разобранный `pcapng` + таблица соединений |
| Бэкап/диски | `robocopy /MIR` с логом, `smartctl`, `Optimize-Volume -ReTrim` | оснастка «Управление дисками» | лог robocopy (код < 8) + атрибуты SMART + хэши |


## Отдельный класс: инструменты без интерфейса

Часть профилей — не приложения, а инструменты: `robocopy`, `dumpcap`, `psql`, `msbuild`,
`gradlew`. У них нет ни окна, ни якорей, и это лучший возможный случай: проверка результата
всегда машинная (лог, XML, хэш), а не «на глаз». Отсюда правило для каталога: если у приложения
есть командный инструмент-спутник (DBeaver → `psql`, Wireshark → `tshark`, Visual Studio →
`msbuild`), профиль описывает **спутник**, а GUI оставляет человеку.

Исключение — операции, которых в CLI нет вообще: настройка вида, привязки MIDI, монтаж по кликам.
Там профиль остаётся UIA-профилем, но с обязательным машинным подтверждением после шага.

## Пять правил, вытащенных из этих профилей

**1. Состояние приложения проверяем не по картинке.** Docker Desktop показывает зелёный кит и
«Engine running», когда демон уже недоступен после сна ноутбука. Единственная честная проверка —
`docker info` с таймаутом. То же с планировщиком: `LastRunTime` врёт меньше, чем зелёная галочка.

**2. Локализация ломает UIA раньше, чем версия.** `TabItem Name='Процессы'` перестаёт
находиться на английской Windows. Поэтому в профилях диспетчера и PowerPoint основной канал —
команды и COM, а Name-якоря помечены как fallback. AutomationId стабильнее: он не переводится.

**3. У каждого приложения есть «свой» формат правды.** Obsidian — это папка markdown, Zotero —
SQLite и локальный HTTP, Terminal — `settings.json`. Писать в формат правды быстрее, чем в UI, и
это же даёт бесплатный офлайн-режим: файл остаётся, даже если приложение не запущено.

**4. Асинхронность — главный источник ложных «получилось».** Everything отвечает мгновенно по
индексу, но индекс отстаёт от диска на секунды; Notion возвращает 200 на создание страницы,
которая ещё не проиндексирована для поиска. Верификация поэтому всегда через второй, независимый
запрос, а не через тот же, что выполнял действие.

**5. Опасные операции почти всегда имеют безопасный предварительный шаг.** `docker system prune`
без `--volumes` не трогает данные; `CloseMainWindow` до `Stop-Process -Force` даёт приложению
сохранить файл; `es.exe -n` с ограничением не грузит диск тысячами путей. Профиль обязан
начинать с безопасного шага, а разрушительный ставить последним и с явным подтверждением.

## Чего в этих профилях нет и почему

- **Нет кликов по координатам.** Даже в tier B: если приложение OpenGL (Ableton, Bitwig), мы идём
  через OSC/Controller API, а если канала нет — честно отдаём приложение визуальному агенту
  (tier C), а не пишем «клик на 745, 320».
- **Нет паролей и токенов.** Notion API и Zotero-коннектор используют ключи из `secrets.enc`;
  в профиле только ссылка на источник секрета.
- **Нет обещания, что это навсегда.** У каждого профиля `verified_at`; UI-дрейф считается нормой,
  и первый признак — не «кнопка не нажалась», а «верификация не прошла».

## Что это меняет в продукте

Профиль перестаёт быть «шпаргалкой по программе» и становится **контрактом**: канал, порядок
шагов, независимая проверка, поведение при провале. Приложение без профиля всё равно работает
(визуальный агент), приложение с профилем работает в 5–20 раз быстрее и не врёт о результате.
Именно поэтому каталог на 122 приложения имеет смысл: покрытие растёт не временем на клики,
а качеством канала.
