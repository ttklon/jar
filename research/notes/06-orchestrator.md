# 06 — Оркестратор: как из фразы получается план и действие

Требование R-15: «сам понимает, каких агентов, скиллы, плагины, MCP-серверы и инструменты нужно».
Требование R-16: «план виден и редактируем до старта».

## 1. Пять слоёв (каждый можно отключить и упростить)

```
фраза/событие
   │
   ▼
[L0 Reflex]      правила, регекспы, хоткеи, «стоп», «громче», «открой X»     ~0 мс, 0 токенов
   │ не распознано
   ▼
[L1 Router]      tiny LLM 0.6–1.7B: интент, слоты, риск, язык, нужен ли план  ~150–400 мс
   │
   ▼
[L2 Planner]     4–8B: декомпозиция на шаги, выбор инструментов из реестра    0.5–3 с
   │
   ▼
[L3 Executor]    детерминированная машина шагов + policy gate + подтверждения
   │
   ▼
[L4 Verifier]    проверка результата (состояние экрана/ФС/ответа) + Critic      по необходимости
```

**Почему слои, а не «одна большая LLM»:** на слабом ПК большая модель = 2 tok/s; правила и
1.7B закрывают 60–70 % бытовых команд мгновенно. И главное — детерминизм там, где он возможен.

## 2. L0: рефлексы (без модели)

Список фраз, которые обязаны срабатывать мгновенно и без «подумать»:
`стоп`, `отмена`, `тише`, `громче`, `пауза`, `повтори`, `что ты сказал`, `открой <известное
приложение>`, `сверни всё`, `заблокируй компьютер`, `запусти таймер на N минут`.

Реализация: конечный автомат + fuzzy-матчинг (расстояние Левенштейна/фонетика) по небольшому
словарю. Это спасает в момент, когда модель занята или зависла: «стоп» должен работать всегда,
даже если ядро перегружено (поэтому обработчик «стоп» живёт в audio-воркере, не в ядре).

## 3. L1: Router (tiny LLM)

Вход: текст + контекст (активное окно, выделение, последние 3 реплики).
Выход строго по JSON-схеме:

```jsonc
{
  "intent": "file.create_folder",       // или "chat", "question", "unknown"
  "slots": { "location": "desktop", "position": "top-right", "name": "Проект X" },
  "risk": "write-local",
  "needsPlan": false,
  "needsTools": ["fs.create_folder"],
  "needsScreen": false,
  "clarify": null,                       // "Какую именно папку?" если не хватает данных
  "lang": "ru"
}
```

Техника: **constrained decoding** (JSON-схема/GBNF) + few-shot из 30–50 примеров + список
интентов, сгенерированный из capability registry. Модель 0.6–1.7B это делает надёжно, если
схема узкая. Если `intent=unknown` дважды — эскалация на L2.

## 4. L2: Planner

Планировщик получает:
1. запрос пользователя (и историю),
2. **отфильтрованный** список инструментов (5–15, retrieval по эмбеддингам + правила),
3. краткую сводку состояния (что открыто, что на экране, что в буфере обмена — с согласия),
4. релевантные «скиллы» (рецепты) из библиотеки,
5. ограничения: бюджет шагов, риск-политика, доступные модели.

Выход — **Plan V2** (см. схему ниже). План показывается в UI: список шагов, у каждого — иконка
риска, ожидаемое время, кнопки «выполнить», «править», «объяснить зачем».

```ts
type Risk = "read" | "write-local" | "destructive" | "external" | "money" | "identity";

interface Step {
  id: string;
  title: string;                 // человеческое: «Создать папку на рабочем столе»
  tool: string;                  // "fs.create_folder"
  args: Record<string, unknown>;
  risk: Risk;
  needsConfirm?: boolean;
  verify?: { kind: "fs.exists" | "window.title" | "screenshot.diff" | "exit.code" | "llm.judge";
             spec: unknown };
  onError?: "retry" | "replan" | "ask" | "abort";
  dependsOn?: string[];
  budgetMs?: number;
}

interface Plan {
  id: string; goal: string; steps: Step[];
  assumptions: string[];         // что мы додумали — показываем пользователю!
  openQuestions: string[];       // что реально стоит уточнить
  estimatedSeconds: number; riskMax: Risk;
  rollback?: { kind: "snapshot" | "git" | "recycle" | "none" };
}
```

**Обязательное поле `assumptions`** — это то самое «переспрашивает»: вместо 10 вопросов до
старта показываем «я понял так: … ; поправь, если нет». Вопросы задаём только когда
неоднозначность меняет риск или необратимость.

## 5. L3: Executor (машина шагов)

Цикл на шаг:

```
1. policy.check(step)        → allow | confirm | deny  (+ объяснение почему)
2. если confirm — ждём пользователя (голос/UI/Telegram), TTL 5 мин
3. lock.acquire(resource)    → mouse/keyboard/clipboard/network — эксклюзивно
4. snapshot if needed        → копия файла / git stash / точка восстановления
5. tool.invoke(args)         → с таймаутом и отменой
6. verify(step.verify)       → факт, а не «модель сказала ok»
7. audit.record(step, result, diff)
8. on failure → onError-политика (retry с изменёнными аргументами → replan → ask → abort)
```

Критичные детали:
- **Один владелец ввода.** Мышь/клавиатура — глобальный мьютекс. Два агента, двигающих мышь
  одновременно, — это гарантированный хаос. Параллелизм — только для действий без ввода.
- **Проверка результата обязательна** для «рук»: после клика смотрим, изменилось ли состояние
  (UIA-дерево/скриншот-диф). Иначе агент «уверенно» кликает 40 раз в пустоту.
- **Loop detection**: хэш `(tool, args, состояние экрана)`; 3 повтора → стоп и вопрос.
- **Step timeout** по умолчанию 60 с (для сборки/тестов — настраиваемо).
- **Отмена** распространяется на дочерние процессы (`taskkill /T` по дереву).

## 6. Скиллы vs свободное планирование

| Подход | Когда |
| --- | --- |
| **Skill (детерминированный рецепт)** | повторяющиеся сценарии: «создай папку», «поставь встречу», «собери релиз». Шаги известны, LLM только заполняет слоты |
| **Планировщик (LLM)** | новые/сложные задачи, где шаги неизвестны |
| **Гибрид (дефолт)** | LLM выбирает skill, если он подходит (retrieval по описанию), иначе планирует |

Скилл — это папка:

```
skills/desktop-folder/
├── skill.json      { id, title, whenToUse[], inputs{schema}, risk, steps[] }
├── run.ts          // опционально: код вместо декларативных шагов
├── verify.ts       // как проверить успех
└── README.md       // человеческое описание
```

Скиллы расширяемы: пользователь может попросить «запомни, как я это делаю» → агент
превращает удачную траекторию в скилл (с проверкой и подтверждением). Это ключ к тому, чтобы
система **ускорялась** от использования, а не деградировала.

> Формат Skill из мира Claude (`SKILL.md` + frontmatter) — хороший ориентир для совместимости,
> см. `sources/orchestration/anthropics__skills/`. Мы поддерживаем импорт таких скиллов.

## 7. Субагенты (агенты-специалисты)

| Субагент | Инструменты | Модель | Особенность |
| --- | --- | --- | --- |
| `researcher` | web.search, fetch, browser.read, файлы | T2/T3 LLM | собирает источники, пишет отчёт с ссылками, ничего не меняет на диске вне workspace |
| `coder` | fs, shell, git, tests, editor | coder-LLM | работает в git-worktree, коммитит атомарно |
| `browser` | playwright/browser MCP | T2 | изолированный профиль браузера |
| `desktop` | mouse/keyboard/UIA/screenshot | T2 + VLM | строгие проверки после каждого действия |
| `media` | yt-dlp, ffmpeg, ASR | T1+ | длинные операции в фоне |
| `assistant` | календарь/почта/заметки | T1+ | всегда подтверждает внешние эффекты |
| `critic` | — | T1/T2 | проверяет план на опасность/бессмысленность |

Правила взаимодействия: субагент **не видит** всю память и все инструменты — только выданные;
результат возвращает структурировано (`{summary, artifacts[], confidence, openQuestions[]}`);
всегда есть «родитель», который решает, продолжать ли.

Протокол между агентами: начинаем с внутреннего (in-process, типизированные сообщения), а
внешнюю совместимость держим через **A2A** (`sources/orchestration/a2aproject__A2A/`) — чтобы
наши агенты могли общаться с чужими.

## 8. Сборка контекста (context engineering)

Бюджет для 8B-модели на 16k: системный промпт 600 токенов, карточки инструментов 1200,
память 800, история 2000, текущая задача 4000, запас 4000.

Приёмы:
1. **Карточки, не схемы целиком**: инструмент описывается 1–2 строками + примерами; полная
   JSON-схема подставляется только для выбранного инструмента.
2. **Скриншот — не текст**: VLM получает изображение, текстовая модель — структурированную
   сводку (элементы, заголовок, ошибки), а не «сырой» OCR на 5 тыс. токенов.
3. **Сжатие истории**: каждые N шагов — суммаризация прошедшего (1.7B моделью), с сохранением
   фактов/решений; сырой лог остаётся в аудите.
4. **Явные маркеры провенанса**: `[tool:fs.read] …` — чтобы модель не путала данные с
   инструкциями (защита от prompt injection, см. `10-safety.md`).

## 9. Модели по шагам (экономия)

| Тип шага | Модель | Почему |
| --- | --- | --- |
| Извлечение слотов | 0.6–1.7B, json | дешево и достаточно |
| Выбор инструмента из 8 | 1.7–4B | точность выше, чем у 0.6B |
| План из 5–15 шагов | 4–8B | нужен «взгляд сверху» |
| Написание кода | coder 7–14B | специализация важнее размера |
| Объяснение ошибки | 4–8B | хватает |
| Проверка «опасно ли» | 1.7B + правила | правила главнее модели |

Правило: **не поднимать модель, пока не провалились дважды** на нижнем уровне (иначе платим
временем за то, что и так работало).

## 10. Наблюдаемость оркестратора

Каждый запуск — трейс:

```
trace(goal) → router(span) → retrieval(span) → plan(span) → step[1..n](spans) → verify → summary
```

Пишем: вход/выход каждого шага, длительность, модель, токены, стоимость (в локальном compute —
«секунды GPU»), артефакты. Из этого автоматически рождаются:
- «почему ты это сделал?» — ответ по трейсу, а не враньё постфактум;
- статистика «какие скиллы чаще» → приоритет автоматизации;
- регрессионные тесты (прогон эталонных сценариев).

## 12. Открытые вопросы

- Хватит ли 4B на планирование в 8 шагов по-русски, или для планов нужен 8B даже на T1
  (с ожиданием 2–4 с)? Решается тестами из `15-evals.md`.
- «Действия кодом» (CodeAgent, как в smolagents) vs «действия JSON-вызовами»: код гибче,
  но опаснее. Гипотеза: код — только в песочнице workspace, с policy gate на импорты.
- Нужен ли отдельный «менеджер плана», переспрашивающий пользователя каждые N минут в долгих
  задачах? Скорее да — но с настройкой «не беспокоить».
