# 08 — Глаза и руки: понимание экрана и действия на рабочем столе

Требования R-05…R-09. Самый сложный и самый «магический» слой. Главный принцип:

> **Действие должно быть проверяемым. Если после действия состояние не изменилось — значит,
> действие не удалось, как бы уверенно ни звучала модель.**

## 1. Три источника восприятия (в порядке приоритета)

| Источник | Что даёт | Стоимость | Надёжность |
| --- | --- | --- | --- |
| **UIA (UI Automation)** | дерево элементов: имя, роль, bounds, состояние, доступные действия | ~5–30 мс, 0 токенов | высокая для «правильных» приложений |
| **OCR (RapidOCR/Tesseract)** | текст где угодно, включая canvas/игры/картинки | 50–200 мс | средняя (без семантики) |
| **VLM (Qwen-VL/UI-TARS/OmniParser)** | семантика: «где кнопка Экспорт», «что за ошибка» | 0.5–5 с | низкая как источник координат, высокая как советчик |

Правильный порядок: **сначала UIA → если элемента нет, OCR+CV → VLM только для понимания и
для выбора из найденных кандидатов**. Клик по координатам «из головы модели» — запрещён
(кроме случаев, когда пользователь явно сказал «кликни в (x,y)»).

## 2. Скриншот: детали, которые ломают всё

- Захват: Win32 GDI/BitBlt или Desktop Duplication API (быстрее, не мигает). На Windows 10 GDI
  надёжнее; на 11 — `Windows.Graphics.Capture` для окон.
- **DPI**: приложение может быть DPI-unaware; координаты в физических пикселях ≠ DIP.
  Всегда получаем `scaleFactor` монитора и конвертируем; тест на 125 %/150 %.
- **Мультимонитор**: виртуальные координаты с отрицательными значениями (левый монитор).
- **HDR**: цвета «выцветают» → при HDR-дисплее делаем tone-mapping для VLM (иначе модель
  не узнаёт тёмные кнопки).
- **Защищённые окна**: скриншот может вернуть чёрный прямоугольник (DRM/банки) — определяем
  и сообщаем: «это окно защищено, я его не вижу».
- **Приватность**: скриншот может содержать пароли/переписку. По умолчанию — не сохраняем;
  если сохраняем (для отладки) — в локальную папку, с автоудалением через N часов.

## 3. UIA: практика

```ts
// псевдокод обёртки над IUIAutomation
const tree = await uia.dump({ windowTitle: /CapCut/, maxDepth: 12, maxNodes: 3000 });
// узел: { id, role:"Button", name:"Export", bounds:{x,y,w,h}, enabled, patterns:["Invoke","Value"] }
await uia.invoke(tree.find({ name: "Export", role: "Button" }));
```

Правила:
- Ищем по `AutomationId` → `Name` → `ControlType` → позиции; `AutomationId` самый стабильный.
- Проверяем `IsOffscreen`, `IsEnabled`, `IsPassword` (пароли не читаем никогда).
- Если приложение — Electron/Chromium без UIA-дерева, включаем accessibility
  (`--force-renderer-accessibility`) или работаем через CDP.
- Дерево может быть огромным (браузер, VS Code) → обрезаем по «видимым» и по глубине,
  кэшируем по `(hwnd, hash)`.
- После каждого действия — повторное чтение **минимального** участка (не всего дерева).

## 4. Клик, ввод, drag: как не промахнуться

| Действие | Как делать правильно |
| --- | --- |
| Левый клик | сначала `SetCursorPos` + задержка 20–40 мс, затем `SendInput` (не `mouse_event`) |
| Двойной клик | интервал 120–180 мс, оба клика в одну точку |
| Ввод текста | `SendInput` с Unicode; для длинных — буфер обмена + `Ctrl+V` (быстрее и не теряет символы), но с восстановлением буфера |
| Горячие клавиши | `SendInput` с keydown/keyup, проверка раскладки (иначе `Ctrl+Z` станет `Ctrl+Я`) |
| Drag | промежуточные шаги 8–12 точек, иначе приложения не распознают |
| Скролл | `WHEEL` по 3–5 строк, с проверкой, что контент сдвинулся |
| Фокус | перед вводом явно фокусируем окно через UIA/`SetForegroundWindow` с обходом foreground-lock |

Дополнительно:
- **Идемпотентность**: перед кликом проверяем «а не сделано ли уже?» (например, диалог уже открыт).
- **Dry-run**: `input.mouse {dryRun:true}` возвращает «я бы кликнул в (842, 317) по кнопке
  Экспорт» — это показывается пользователю в режиме «покажи, что будешь делать».
- **Пауза после действия** (150–400 мс) + ожидание «UI успокоился» (сравнение хэшей скриншота
  до/после), а не `sleep(2000)`.

## 5. «Папка в правом верхнем углу рабочего стола» (R-05)

Пример, который показывает, почему нельзя «просто создать папку».

1. Рабочий стол — это `ListView` с иконками; позиции хранятся в реестре/`desktop.ini` или
   вычисляются оболочкой.
2. Вариант A (правильный, стабильный): создать папку (`fs.mkdir` в `%USERPROFILE%\Desktop`),
   затем **разместить иконку** через `IFolderView2::SelectAndPositionItems` (COM, требует
   обхода через `shell32`/`windows-rs`) — либо через имитацию «Auto arrange off» + drag.
3. Вариант B (простой, но хрупкий): скриншот → найти свободное место в правом верхнем углу →
   drag иконки мышью туда.
4. Вариант C (честный fallback): создать папку и сказать «создал, но Windows не даёт мне
   расставить иконки — включите «Упорядочить автоматически: выкл», тогда поставлю».

Мы делаем A с fallback на C (B — только по просьбе «поставь руками»). Это ровно тот случай,
когда «агент должен уметь признавать границы».

## 6. CapCut / видеомонтаж «вместе со мной» (R-09)

Сценарий: пользователь в приложении, агент ведёт по шагам, обсуждая.

Требуется:
1. **Определить приложение**: по заголовку окна/процессу; переключиться в «режим наставника».
2. **Знать контекст**: что на таймлайне (скриншот + OCR), какая панель открыта.
3. **Пошаговый режим**: агент предлагает шаг → ждёт подтверждения («делай» / «покажи» /
   «пропусти») → выполняет или подсвечивает область (оверлей с рамкой).
4. **Обучение по ходу**: пользователь делает руками — агент записывает последовательность
   (UIA-события + клики) и предлагает «сохранить как скилл».
5. **Проверки**: после каждого шага — «получилось? вижу новый клип на таймлайне».

КапCut — Electron-приложение (риск: кастомный UI, слабое UIA-дерево) → делаем ставку на
скриншот + OCR + запоминание координат (они стабильны в пределах разрешения) + визуальные
якоря (шаблоны кнопок). Отдельный «профиль приложения» (как в Playwright): набор известных
элементов, шагов и проверок, который можно пополнять.

```jsonc
// profiles/capcut.json
{
  "match": { "process": "CapCut.exe", "titleIncludes": "CapCut" },
  "anchors": [
    { "id": "export", "kind": "template", "image": "anchors/capcut-export.png", "dpi": [100,125,150] },
    { "id": "timeline", "kind": "region", "rel": [0, 0.62, 1, 0.38] }
  ],
  "skills": ["capcut.trim", "capcut.split", "capcut.addText"],
  "confidence": 0.82
}
```

> Это же решение масштабируется на Photoshop, Premiere, Excel, 1C — «профили приложений»
> становятся главным способом сделать агента реально полезным в конкретных программах.

## 7. Верификация результата (обязательный шаг)

| Тип шага | Проверка |
| --- | --- |
| Файловая операция | `fs.exists` + размер/хэш/время изменения |
| Клик по кнопке | изменение UIA-дерева или diff скриншота в области |
| Ввод текста | чтение значения поля (UIA `Value`) — совпадает |
| Запуск программы | процесс появился + главное окно (заголовок) |
| Команда в терминале | exit code + отсутствие паттернов ошибок в stderr |
| Открытие страницы | `document.readyState`/заголовок/наличие элемента (через браузерный инструмент) |
| Видео «пересказано» | есть транскрипт длиной ≥ N слов, таймкоды монотонны |

Если проверка невозможна — честно пишем в отчёте «выполнил, но подтвердить не могу» и
предлагаем пользователю посмотреть.

## 8. Производительность восприятия

- Скриншот 1080p → даунскейл до 1280 px по длинной стороне для VLM (иначе 1500+ токенов и
  медленно). Для OCR — наоборот, оригинал/2x для мелкого текста.
- Кэш UIA-дерева на 300 мс; инвалидация по событию `UIA_StructureChanged`.
- OCR только по регионам интереса (окно в фокусе, панель), а не весь экран.
- VLM вызываем **не чаще 1 раза на шаг** и только если UIA+OCR не дали ответа.

## 9. Ограничения, которые честно признаём

- Игры с анти-читом: не трогаем (бан пользователю не нужен).
- Окна с защитой контента: не видим.
- Приложения, рисующие свой UI (Qt/canvas/игры): только OCR + шаблоны, точность ниже.
- Анимации/переходы: ждём стабилизации, иначе клик уходит «в пустоту».
- UAC/админ-диалоги: показываем пользователю, не пытаемся обойти.

## 11. Внешние данные (срез 2026, для ориентира по ожиданиям)

- UI-TARS-1.5-7B: OSWorld ~42.5 (100 шагов), WindowsAgentArena ~42.1 — то есть **лучшие
  открытые агенты решают меньше половины реальных задач**; не обещаем «всё».
- UI-TARS-2 в WindowsAgentArena ~50.6; Agent S3 ~50–56. OSWorld 2.0 (2026) — < 25 % бинарного
  успеха у топовых моделей при ~318 вызовах инструментов на задачу.
- Вывод для продукта: (а) узкие навыки с проверками важнее «универсального агента»;
  (б) обязательны чекпойнты и человек в цикле; (в) метрика «задача выполнена и подтверждена»,
  а не «агент сказал, что выполнена».

## 12. Открытые вопросы

- Свой Rust-хелпер для ввода/UIA/ScreenCapture (стабильно, но долго) vs `nut-js` + `windows-rs`
  вперемешку (быстро, но зависимо от заброшенного пакета). Склоняюсь к своему хелперу
  (500–800 строк) — это фундамент, на котором всё стоит.
- Как хранить «профили приложений»: локально + шаринг через сообщество (с проверкой)?
- Нужен ли «режим показа» (агент подсвечивает элемент вместо клика) как отдельный дефолт
  для новых приложений? Гипотеза: да, для незнакомых приложений — сначала показывать.
