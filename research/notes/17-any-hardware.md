# 17 — Оптимизация под любое железо: от 4 ГБ без GPU до 32 ГБ с RTX

Требование R-14 + R-28: «подстраивается под любой компьютер, не забивает ресурсы, работает
даже на слабом». Это не одна настройка, а **лестница рычагов**, где каждый следующий включается,
только если предыдущие исчерпаны.

## 1. Физика: почему всё упирается в память

Декодирование токена — это чтение **всех** весов модели из памяти. Значит:

```
tok/s ≈ (эффективная пропускная способность памяти) / (байт на параметр за токен)
bytes/token ≈ params × bytesPerWeight
```

| Железо | BW (эфф.) | 1.7B Q4 | 4B Q4 | 8B Q4 | 14B Q4 |
| --- | --- | --- | --- | --- | --- |
| DDR4-2400 dual (старый ноут) | ~30 ГБ/с | ~10 | ~4 | ~2 | ~1 |
| DDR5-5600 dual | ~70 ГБ/с | ~24 | ~10 | ~5 | ~3 |
| iGPU (Iris Xe, shared) | ~50 ГБ/с | ~17 | ~7 | ~3.5 | ~2 |
| RTX 3050 4 ГБ | ~224 ГБ/с | ~75 | ~32 | (не влезет) | — |
| RTX 4060 8 ГБ | ~272 ГБ/с | ~90 | ~38 | ~19 | (край) |
| RTX 4070 Ti 12 ГБ | ~504 ГБ/с | ~170 | ~72 | ~36 | ~21 |
| RTX 4090 24 ГБ | ~1008 ГБ/с | ~340 | ~144 | ~72 | ~41 |

*Оценки порядка величины при идеальном offload. Реальность ниже на 20–40 % из-за оверхеда,
квантования, attention и неэффективного батча. **Всегда проверяем калибровкой** (`02-hardware-profiler.md`).*

Prefill (обработка промпта) наоборот **compute-bound**: 1000 токенов промпта на CPU могут
занять 3–8 с. Поэтому в агентском цикле главный враг — не длина ответа, а **длина промпта**.

## 2. Лестница рычагов (по убыванию эффекта)

| # | Рычаг | Выигрыш | Цена |
| --- | --- | --- | --- |
| 1 | **Размер модели** 8B→4B→1.7B→0.6B | 2× на каждый шаг | качество |
| 2 | **Квант** Q8→Q5→Q4_K_M→IQ3/IQ2 | ~1.9× на шаг Q8→Q4 | немного качества |
| 3 | **Контекст** 32k→8k→4k | линейно по KV-памяти | «забывчивость» на длинных задачах |
| 4 | **KV-квант** f16→q8_0→q4_0 | 2–4× меньше KV | чуть хуже длинные диалоги |
| 5 | **Бэкенд** CPU→Vulkan→CUDA/OpenVINO | 3–20× | вес бинарников, драйверы |
| 6 | **Частичный offload** `-ngl` | линейно до потолка VRAM | подбор, риск OOM |
| 7 | **Потоки** = физ. ядра − 1 (обычно 4–8) | +20–40 % против 1 потока; лишние — вредят | — |
| 8 | **Flash attention + batch/ubatch** | 10–30 % на длинном контексте | совместимость |
| 9 | **Кэш префикса** (system+tools) | −30–60 % prefill в агентском цикле | реализация |
| 10 | **Спекулятивное декодирование** (draft 0.5B) | 1.4–2.2× на предсказуемом тексте | +RAM, сложность |
| 11 | **Каскад моделей** (1.7B → 4B → 8B) | 2–5× по среднему времени | логика эскалации |
| 12 | **Сжатие промпта** (LLMLingua, обрезка карточек) | −40–70 % токенов | риск потери деталей |
| 13 | **ОС-уровень** (приоритеты, EcoQoS, исключения AV) | 5–25 % | настройки пользователя |
| 14 | **Планирование** (тяжёлое — в простое/на AC) | «не мешает» | задержка задач |

**Правило:** сначала 1–2 (модель и квант), потом 3–4 (контекст), только потом 9–12 (умная
инженерия). Начинать с «оптимизации промптов» на 8B, которая не влезает в 8 ГБ — ошибка.

## 3. Кванты: практическая таблица

| Квант | Б/параметр | 4B | 8B | Качество (относительно F16) | Когда |
| --- | --- | --- | --- | --- | --- |
| F16 | 2.00 | 8.0 ГБ | 16.0 ГБ | 100 % | только если памяти валом |
| Q8_0 | 1.06 | 4.4 | 8.6 | ~99.9 % | embedding/OCR/rerank, маленькие модели |
| Q6_K | 0.82 | 3.4 | 6.7 | ~99.5 % | есть запас VRAM |
| **Q5_K_M** | 0.70 | 2.9 | 5.7 | ~99 % | **лучший баланс на 1–4B** |
| **Q4_K_M** | 0.56 | 2.4 | 4.7 | ~97–98 % | **дефолт** |
| IQ4_XS | 0.51 | 2.1 | 4.2 | ~96 % | когда не хватает 200 МБ |
| Q3_K_M | 0.44 | 1.8 | 3.7 | ~93 % | T0/T1, «лишь бы работало» |
| IQ2_XXS | 0.26 | 1.1 | 2.2 | ~80 % (ломается на коде) | экстрим, не для кода |

Важно: **на моделях < 4B квантовать агрессивно нельзя** — падение качества непропорционально
велико. Лучше взять 1.7B в Q5, чем 4B в IQ2.

Importance matrix (imatrix) даёт +1–3 % качества при том же размере — стоит делать для
своих сборок, если будем публиковать кванты.

## 4. KV-кэш: скрытый пожиратель

```
KV = 2 × layers × kv_heads × head_dim × ctx × bytes
```
Пример 8B (32 слоя, GQA 8×128), 8k контекст:
- f16: 2×32×1024×8192×2 = **1.07 ГБ**
- q8_0: ~0.54 ГБ
- q4_0: ~0.27 ГБ

Для 32k контекста умножаем на 4 → 4.3 ГБ f16. Отсюда правило: **на 8 ГБ VRAM держим 8B
с контекстом 8k и q8_0 KV**, а не 8B с 32k (который вылетит в shared memory и упадёт в 10 раз
по скорости — см. §6).

## 5. Пропускная способность vs задержка в агентском цикле

Типичный шаг агента: промпт 4–6k токенов (система + инструменты + история + скриншот-сводка),
ответ 150–400 токенов.

| Сценарий (8B Q4, RTX 4060) | Prefill | Decode | Итого |
| --- | --- | --- | --- |
| Без кэша префикса, 6k промпт | ~2.2 с | ~4 с | **6.2 с** |
| С кэшем префикса (3k переиспользовано) | ~1.1 с | ~4 с | **5.1 с** |
| Промпт сжат до 2.5k + кэш | ~0.6 с | ~3 с | **3.6 с** |
| Каскад: 1.7B решил задачу без эскалации | ~0.3 с | ~0.6 с | **0.9 с** |

Вывод: **каскад + кэш + сжатие дают больше, чем переход на GPU следующего класса.**

## 6. Ловушки Windows, которые убивают производительность

| Ловушка | Что происходит | Лечение |
| --- | --- | --- |
| **VRAM oversubscription (WDDM)** | превысили VRAM на 100 МБ → драйвер выгружает в системную RAM, скорость падает в 5–20 раз | держать запас ≥ 0.6–0.8 ГБ, проверять `nvidia-smi` перед загрузкой |
| Optimus / гибридная графика | приложение тихо садится на iGPU | явный выбор адаптера, `NvOptimusEnablement`, подсказка пользователю |
| Defender сканирует GGUF | чтение 5 ГБ модели при каждом старте | исключение для папки моделей (с согласия) |
| Энергосбережение (EcoQoS) | Windows режет частоты фоновым процессам | `SetProcessInformation/EcoQoS` выключаем для инференса, включаем для UI |
| Power plan «Экономия» | −30–50 % CPU-скорости | проверять и предупреждать |
| HDD + mmap модели | стохастические фризы по 2–5 с | не грузить > 1 ГБ моделей с HDD; предзагрузка в RAM |
| Антивирус на `llama-server.exe` | случайные таймауты | подпись бинарника, каталог в исключениях по желанию |
| Перегрев ноутбука | троттлинг через 10 мин работы | следить за температурой, снижать потоки, пауза |
| Фоновые обновления Windows | диск/CPU 100 % | пауза тяжёлых задач, уведомление |
| Мультимонитор 4K | скриншоты 3840×2160 → OCR/VLM медленно | даунскейл (1280 px) для VLM, кроп для OCR |
| 125–150 % DPI | координаты кликов мимо | пересчёт DIP↔px, тесты на всех масштабах |

## 7. Профили конфигураций (что ставим на что)

| Tier | Железо | LLM | ASR | TTS | VLM | Ожидание (p50) |
| --- | --- | --- | --- | --- | --- | --- |
| **T0** | 4–8 ГБ RAM, 2 ядра, HDD | 0.6–1.7B Q4, ctx 2k | whisper base Q5 (`--threads 2`) | Piper (CPU) | нет (UIA+OCR) | ответ 2–4 с, «руки» 0.3 с |
| **T1** | 8–16 ГБ, 4–8 ядер, iGPU | 1.7–4B Q4/Q5, ctx 4–8k | turbo Q5 / small | Kokoro CPU | Qwen2.5-VL-3B Q4 (по требованию) | ответ 1.5–3 с |
| **T2** | 16–32 ГБ, 6–12 ГБ VRAM | 4–8B Q4, ctx 8–16k | turbo Q5 на GPU | Kokoro GPU | 3B VLM резидентно | ответ 0.8–1.5 с |
| **T3** | 32+ ГБ, 16–24 ГБ VRAM | 8–14B Q4/Q5 или 30B-A3B | turbo/Parakeet | Chatterbox/Qwen3-TTS | 7B VLM | ответ 0.5–1 с, две модели параллельно |

Для каждого tier — свой `model-lock.json` и свои лимиты:
`{maxCtx, maxParallel, keepAliveMin, prefetch: [asr, vad, embed], lazy: [vlm, tts]}`.

## 8. Эластичное поведение в рантайме

Сигналы (опрос 2 с): свободная RAM/VRAM, загрузка CPU/GPU, температура, питание, полноэкранное
приложение в фокусе, простой пользователя, очередь задач.

| Условие | Действие |
| --- | --- |
| RAM < 1.5 ГБ свободно | выгрузить VLM/кодер, снизить ctx, предупредить |
| VRAM > 70 % | не грузить новые модели, `-ngl` вниз |
| Пользователь в игре/видео (fullscreen) | пауза фоновых LLM-задач, оставить только PTT-ответы |
| Батарея < 30 % и не на зарядке | пауза тяжёлых джобов, ASR small, TTS Piper |
| Температура > 85 °C | −2 потока, пауза на 2 мин, уведомление |
| Простой > 5 мин | предзагрузка «горячего» набора моделей, консолидация памяти |
| Очередь > 5 задач | батчинг, «сначала быстрые», отчёт «сделаю к 18:40» |

Всё это видно в UI одной полосой: «Экономлю ресурсы (игра в фокусе)» — пользователь понимает,
почему агент «тормозит».

## 9. Холодный старт и память приложения

Цели: cold start ≤ 3 с до интерактивного окна, RAM в простое ≤ 300 МБ (без моделей),
«первый ответ» ≤ 5 с после запуска (ASR+VAD уже загружены, LLM — по требованию).

Как добиваемся:
- `asar` + `asarUnpack` только для бинарников; lazy-`import` тяжёлых модулей;
- ядро в `utilityProcess` стартует параллельно с окном;
- VAD/wake-word — крошечные ONNX, грузим сразу (нужны для «слушаю»);
- LLM-процесс спавним по первому запросу, «прогрев» — в простое;
- рендерер: без тяжёлых библиотек в первом чанке, code-splitting, виртуализация логов;
- ограничение логов в памяти (ring buffer 5 тыс. записей), запись на диск — батчами.

## 10. Энергия (для ноутбуков)

- Always-on слух (VAD+wake) — это ~1–3 % CPU, ONNX INT8; на NPU ещё дешевле.
- LLM — только по требованию; «keep-alive» отключается на батарее.
- tok/s на ватт — метрика для выбора модели на ноутбуке; считаем из калибровки (энергия
  через `powercfg /batteryreport` + время).
- «Тихий режим»: 1 поток, меньший контекст, TTS Piper — чтобы вентилятор не включался.

## 11. Как доказывать, что стало быстрее

- `pnpm bench:inference --profile=profiles/t1.json` — прогон 20 промптов, отчёт p50/p90.
- CI perf-smoke: старт, память, «первый ответ» — падение > 20 % от baseline = красный.
- В UI — «ожидаемо/фактически» для каждой модели; расхождение > 30 % → предложить пересчёт.
- Все замеры — на одном и том же наборе промптов и с фиксированными версиями моделей.

## 12. Антипаттерны

1. «Просто поставь 8B на всё» → на 8 ГБ RAM это 2 tok/s и разочарование.
2. Занимать 100 % VRAM → WDDM-спилл и падение в разы.
3. Контекст 32k «по умолчанию» → KV съедает память, prefill убивает латентность.
4. Держать 3 модели резидентно → OOM при первом же скриншоте.
5. Эмбеддить всё подряд на каждое действие → диск и CPU в потолок.
6. Python в горячем пути (каждый клик) → +50–200 мс на пустом месте.
7. Оптимизировать промпт, не посмотрев в профилировщик (обычно виноват не промпт).

## 14. Открытые вопросы

- Спекулятивное декодирование в `llama-server` на Windows: стабильно ли с Qwen3 (draft 0.6B +
  8B)? Нужен замер acceptance rate; если < 60 % — не окупается.
- Кэш префикса между шагами агента: `llama-server` умеет (`--prompt-cache`), но инвалидируется
  при смене картинки/инструментов. Нужна стратегия «стабильный префикс + изменяемый хвост».
- NPU (Intel AI Boost / AMD IPU): реальный выигрыш на VAD/OCR/embed — да; на LLM 4B — пока
  нет (OpenVINO-путь сырой). Проверить на 2–3 машинах.
- Стоит ли делать «лёгкий профиль» с whisper base вместо turbo на T0 — по качеству русского
  base заметно хуже; возможно, лучше turbo Q4 на 2 потоках.
