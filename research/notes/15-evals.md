# 15 — Оценки: как понять, что стало лучше, а не «кажется»

Без собственных замеров любая смена модели/промпта — это вера. Здесь — минимальная, но
честная система оценки. Всё локально, без облачных сервисов.

## 1. Что меряем

| Слой | Метрика | Как |
| --- | --- | --- |
| **ASR** | WER/CER на русском (команды и свободная речь), доля галлюцинаций на тишине | эталонные 20–30 записей |
| **Router (интент)** | точность интента и слотов | 100 размеченных фраз |
| **Tool selection** | top-1 точность выбора инструмента, точность аргументов (exact match по полям) | 60 кейсов |
| **Планирование** | доля планов, прошедших валидатор + оценку критика; среднее число шагов | 30 задач |
| **Исполнение** | доля задач, завершённых и **подтверждённых проверкой** | 25 сценариев на ВМ |
| **Кодинг** | доля задач с зелёными тестами; шагов до успеха; регрессии | 20 задач |
| **Латентность** | end-of-speech → первый звук; TTFB LLM; шаг инструмента | 100 прогонов |
| **Ресурсы** | пик RAM/VRAM, tok/s, температура | профилировщик |
| **Безопасность** | доля отказов на опасные/инъекционные кейсы (должно быть 100 %) | 40 атакующих кейсов |
| **Стабильность** | падения на 24-часовом прогоне, утечки памяти | soak-тест |

## 2. Датасеты (свои, маленькие, версионированные)

```
evals/
├── asr/ru-commands/          # wav + эталонный текст
├── router/intents.jsonl      # {text, intent, slots}
├── tools/selection.jsonl     # {query, expect_tool, expect_args}
├── plans/tasks.jsonl         # {goal, constraints, must_include_steps[]}
├── desktop/scenarios.yaml    # шаги на ВМ + проверки
├── coding/tasks/             # репо-заготовки + тесты (как mini-SWE-bench)
└── security/attacks.jsonl    # инъекции, опасные команды, утечки
```

Правила: 50–100 кейсов на слой достаточно, чтобы увидеть регрессию; расширяем по мере
появления реальных багов (каждый баг → кейс; это важнее, чем «ровные» синтетические наборы).

## 3. Как прогонять

```bash
pnpm evals --suite=router --models=qwen3-1.7b,qwen3-4b,gemma3-4b
pnpm evals --suite=tools  --profile=T1 --report=out/report.html
pnpm evals --suite=security --fail-under=1.0     # в CI, блокирует merge
```

- Прогон на **целевых tier'ах** (T1 — самое важное: там модели слабые).
- Детерминизм: `temperature=0` где возможно, фиксированные сиды, фиксированные версии моделей
  (по sha256 из `model-lock.json`).
- LLM-as-judge — только для «качества текста», и только с калибровкой на 30 ручных оценках.

## 4. Что считаем «хорошо» для v1

| Метрика | Порог |
| --- | --- |
| WER команд (ru) | ≤ 12 % |
| Точность интента | ≥ 92 % |
| Точность выбора инструмента (top-1) | ≥ 90 % |
| Точность аргументов | ≥ 85 % |
| Успех desktop-сценариев (с проверкой) | ≥ 70 % |
| Кодинг: зелёные тесты с первой попытки | ≥ 40 % |
| Латентность «услышал → заговорил» | ≤ 1.5 с (p50) |
| Отказы на security-кейсах | 100 % |
| Падения за 24 ч soak | 0 |

## 5. Регрессионные тесты в CI

- `security` и `unit/contract` — на каждый PR (быстро).
- `router/tools` — на PR, затрагивающих промпты/реестр/модели (по `paths-filter`).
- `desktop` — nightly (нужна ВМ; используем Windows-раннер + `WindowsAgentArena`-подобные
  сценарии на простых приложениях: Блокнот, Проводник, Калькулятор, наш собственный демо-стенд).
- Отчёт — артефакт CI + график тренда в репозитории (`evals/history/*.json`).

## 6. Оценка «в поле» (у пользователя)

- Локальная статистика: доля успешных шагов, частые ошибки, «сколько раз переспросил».
- **Только по явному согласию** и **только агрегаты**, без текстов команд; экспорт в файл,
  пользователь сам решает, отправить ли.
- Кнопка «это было плохо» на любом шаге → сохраняет контекст (локально) в `bad-cases/`,
  чтобы потом добавить в датасет.

## 7. Анти-паттерны (чего не делаем)

- Не гонимся за лидербордами: они не про русский, не про Windows-UI и не про наш бюджет.
- Не меряем «средним по больнице»: интересует p50/p90 и худшие 10 % кейсов.
- Не сравниваем модели разными промптами (нечестно): промпт фиксируется, меняется одна вещь.
- Не принимаем решение по 3 примерам: минимум 30.
- Не оптимизируем метрику в ущерб безопасности: security-порог не двигается.

## 9. Открытые вопросы

- Нужен ли «золотой» набор из реальных задач пользователя (с его согласия, локально)? Да —
  это лучший датасет, но требует согласия и аккуратной анонимизации.
- Как автоматически оценивать «полезность» ответа (не только корректность)? Пока — ручная
  оценка 20 примеров раз в две недели.
- Стоит ли завести публичный мини-лидерборд для русских desktop-команд? Потенциально — да,
  это и маркетинг, и вклад в сообщество.
