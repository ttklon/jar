# 20 — Самообучение и саморасширение: как он «достаёт» то, чего не умеет

Требование: «если под задачу нет ни агента, ни MCP-сервера, ни скилла, ни коннектора — пусть
ищет, как эту возможность приобрести, и доустанавливает, уведомляя меня».

Это самая опасная функция продукта. Ниже — как сделать её так, чтобы она приносила пользу,
а не превращала компьютер в бэкдор.

## 1. Четыре механизма «научиться» (от безопасного к рискованному)

| # | Механизм | Что происходит | Риск |
| --- | --- | --- | --- |
| 1 | **Композиция существующего** | задача решается комбинацией уже установленных инструментов (план из 3 шагов) | нет |
| 2 | **Синтез скилла** | агент обобщает удачную траекторию в скилл-рецепт и сохраняет его | низкий (наш формат, наши инструменты) |
| 3 | **Установка готового расширения** | находит MCP-сервер / плагин / коннектор / модель и ставит | **средний/высокий** |
| 4 | **Написание своего расширения** | генерирует код MCP-сервера/скилла и запускает в песочнице | высокий |

Правило: **всегда пробуем 1 → 2, и только потом 3 → 4.** В 70–80 % случаев «не умею» — это
«не догадался скомбинировать».

## 2. Детектор пробела (когда вообще начинать искать)

Признаки, что нужна новая способность:
- планировщик 2 раза подряд вернул `no_suitable_tool` для одного класса задач;
- шаг упал с `unsupported`/`not_found` (нет API, нет инструмента);
- пользователь сказал «это можно сделать через X» — прямая подсказка;
- задача выполнена «руками» (через UIA) успешно 3 раза → кандидат на автоматизацию.

Анти-признак: **не искать расширения для разовой задачи** — дороже, чем сделать руками.

## 3. Поиск кандидатов

| Источник | Что даёт | Как искать |
| --- | --- | --- |
| Официальный реестр MCP | проверенные записи, версии, transport | `modelcontextprotocol/registry` API |
| Каталоги сообщества | широта (1400+ серверов) | наш инвентарь `discovery/mcp-servers.json` + punkpeye/wong2 списки |
| GitHub | всё остальное | поиск по топикам `mcp-server`, `model-context-protocol`, язык, звёзды |
| npm / PyPI | пакеты с бинарями | `npm search`, `pypi` JSON API, keyword |
| Awesome-листы | курирование человеком | уже скачаны в vault |
| Сам ZShelper | свои скиллы и профили приложений | локальная библиотека |

## 4. Оценка (gate перед установкой)

Автоматический скоринг + жёсткие стоп-условия:

| Проверка | Стоп-условие |
| --- | --- |
| Лицензия | GPL/AGPL/«research only»/нет лицензии → **не ставим молча**, только по явному согласию |
| Свежесть | нет коммитов > 18 мес → предупреждение; > 36 мес → не ставим |
| Архивность | `archived: true` → не ставим |
| Популярность | ★ < 20 и нет в официальном реестре → «не рекомендуется» |
| Права | запрашивает больше, чем нужно для задачи → отказ/сужение |
| Сеть | требует внешний сервис/ключ → отдельный класс «нужен аккаунт» |
| Пост-инсталл скрипты | `postinstall`, `preinstall` → устанавливаем с `--ignore-scripts` |
| Размер | > 200 МБ → предупреждение |
| Шум | тысячи файлов/зависимостей → предупреждение |

Пользователю показываем **карточку решения**: что это, зачем, что получит доступ, чего лишится,
сколько весит, чем рискуем, «установить / отменить / показать исходники».

## 5. Установка в изоляции

```
%APPDATA%/ZShelper/extensions/
├── mcp/<id>/                 # свой node_modules, свой lockfile
│   ├── package.json          # pinned version, --ignore-scripts
│   ├── package-lock.json     # фиксация дерева зависимостей
│   ├── manifest.json         # от нашего имени: права, риск, источник, sha
│   └── signature.json        # хэш пакета + Ed25519-подпись каталога
└── skills/<id>/              # наши скиллы (JSON+TS, без зависимостей)
```

Правила:
1. **Пиннинг версий** и `package-lock.json`; обновление — только через наш review.
2. `--ignore-scripts` всегда (иначе `postinstall` = произвольный код на этапе установки).
3. Отдельный `cwd`, минимальный `env`, **без наследования токенов** других серверов.
4. Запуск под ограниченным токеном (AppContainer/Job Object) там, где возможно.
5. Сетевой доступ — через наш прокси с allowlist; по умолчанию `net:none` для локальных серверов.
6. **Smoke-test в песочнице**: `tools/list`, один безопасный вызов, проверка, что не выходит
   за разрешённые пути. Провал → «не работает, удалить?».

## 6. Регистрация и права

После установки создаётся `Capability` (см. `01-architecture.md` §4) с:
- `risk` — вычисляется по имени/схеме/аннотациям + ручная разметка для популярных;
- `permissions` — минимальные, сужаемые пользователем;
- `provenance` — откуда взято, кем подписано, когда;
- `health` — ping/версия/ошибки.

**Новый инструмент никогда не получает `allow` на `destructive` автоматически.** Первые N вызовов —
с подтверждением («обучение доверием»).

## 7. Синтез скиллов из опыта

```
наблюдение траектории (UIA + вызовы инструментов + скриншоты)
   → сегментация на шаги
   → обобщение переменных (имена файлов, координаты → якоря)
   → проверка: воспроизвести 2 раза в песочнице
   → предложение пользователю: «сохранить как навык "Экспорт из CapCut"?»
   → сохранение с тестами и описанием whenToUse
```

Скилл хранится как данные (JSON) + опциональный код. Всё, что делает скилл, проходит через
тот же policy gate — скилл **не может** обойти права.

Оценка полезности: сколько раз применён, доля успеха, сколько секунд сэкономлено. Скиллы с
низким success rate — на «доработку» или в архив.

## 8. Самообучение маршрутизации (тихо и безопасно)

Отдельно от установки расширений: система учится **выбирать модель/инструмент** лучше.
- Из аудита считаем: для класса задач `X` модель `M` дала успех 78 % (n=143).
- Обновляем таблицу маршрутизации, но только при `n ≥ 30` и приросте > 5 п.п.
- Изменения — за флагом «экспериментальная маршрутизация», с возможностью откатить одним кликом.
- Никогда не учимся на «пользователь согласился» как на «действие было правильным».

## 9. Безопасность цепочки поставок (главный чеклист)

| Угроза | Контрмера |
| --- | --- |
| Typosquatting (`server-filesystm`) | сверяем имя с реестром, показываем «похоже на известный пакет» |
| Захват популярного пакета | пиннинг + `lockfile` + проверка, что изменился только ожидаемый код |
| Вредоносный `postinstall` | `--ignore-scripts`, просмотр списка скриптов до установки |
| Prompt injection в описании инструмента | описания — `untrusted`, показываем пользователю и режем «инструкции» |
| Сервер читает всё подряд | allowlist путей, явные права на папки |
| Сервер «звонит домой» | сетевой прокси, allowlist доменов, лог всех запросов |
| Подмена обновления расширения | подпись каталога, отзыв версий (revocation list) |
| Расширение-вымогатель | карантин: расширения без вызовов 30 дней → автоотключение |

Плюс: раз в неделю — «аудит расширений» (что установлено, что давно не используется, что
просит больше прав, чем при установке).

## 10. Чего не делаем никогда (даже если пользователь просит «поставь всё»)

1. Не ставим драйверы, службы, античит-обходы, «оптимизаторы» реестра.
2. Явно не устанавливаем расширения, требующие отключения Defender/обновлений.
3. Не запускаем неподписанные `.exe`, `.bat`, `.ps1` из интернета без показа содержимого.
4. Не даём расширению доступ к секретам других расширений.
5. Не устанавливаем ничего в системные папки (`C:\Windows`, `Program Files`) без UAC-подтверждения.

## 11. UX саморасширения

- Карточка: «Не умею „сделать скриншот с прокруткой“. Нашёл 3 варианта: … Рекомендую B (MIT,
  12 тыс. звёзд, локальный). Установить?»
- «Почему ты это предлагаешь» → объяснение пробела + что изменится.
- Настройки: «разрешить самостоятельно устанавливать расширения» (по умолчанию — **спрашивать**),
  «только из официального реестра», «максимум N расширений», «бюджет на эксперименты».
- Журнал: что установлено, кем инициировано, сколько раз использовано, «удалить».
- Уведомление в Telegram: «🔧 Установил расширение X (MCP, MIT). Права: чтение папки Загрузки».

## 13. Открытые вопросы

- Как валидировать «сгенерированный» MCP-сервер, чтобы он не имел права делать больше
  разрешённого? Нужен статический анализ (AST) + песочница с фейковой ФС.
- Нужен ли собственный **каталог рекомендованных** расширений с ревью (как «проверено ZShelper»)?
  Гипотеза: да, 30–50 проверенных серверов закрывают 90 % задач.
- Сколько времени ждать подтверждения от пользователя, прежде чем считать «не сейчас» и
  продолжать задачу обходным путём? Гипотеза: 3 минуты, затем — план B.
