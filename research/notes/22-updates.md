# 22 — Система обновлений: как правки доезжают до всех, кто поставил .exe

Требование: приложение установлено у людей, я выпускаю улучшения → обновления приходят
**автоматически, безопасно и бесплатно**, через GitHub.

## 1. Базовая схема (без своего сервера)

```
разработчик:  git tag v1.4.0 → GitHub Actions → сборка → подпись → Release (assets + latest.yml)
                                                                        │
пользователь: приложение раз в 6 ч → GET releases/latest (или latest.yml)│
              → сравнение semver → скачивание (дельта, если есть)      │
              → проверка подписи и sha512 → установка при выходе/по кнопке
```

Компоненты: `electron-builder` (генерация `latest.yml` + blockmap), `electron-updater`
(загрузка/установка), GitHub Releases (хостинг, бесплатно для публичного репо).

Для OSS есть и «совсем бесплатный» путь без GitHub API-лимитов: `update.electronjs.org`
(отдаёт обновление по схеме `owner/repo`), но он работает только для публичных репозиториев и
только с GitHub Releases.

## 2. Каналы и поэтапный выкат (rollout)

| Канал | Кто получает | Как |
| --- | --- | --- |
| `stable` | все | обычный Release |
| `beta` | «хочу новое» | GitHub **pre-release** + `channel: beta` |
| `alpha`/`nightly` | разработчик | pre-release + отдельная ветка |

GitHub не умеет «10 % пользователей». Поэтому вводим **свой манифест** (файл в репозитории,
например `updates/manifest.json`, отдаваемый через `raw.githubusercontent.com` или gh-pages):

```jsonc
{
  "schema": 1,
  "channel": "stable",
  "latest": "1.4.0",
  "minSupported": "1.2.0",           // ниже — принудительное обновление (breaking)
  "rollout": { "1.4.0": 0.1 },       // 10 % по стабильному хэшу user_id
  "releasedAt": "2026-11-08T10:00:00Z",
  "notes": "…markdown, человеческим языком…",
  "files": [
    { "name": "ZShelper-1.4.0-Setup.exe", "size": 94215680,
      "sha512": "…", "url": "https://github.com/ttklon/jar/releases/download/v1.4.0/…" }
  ],
  "mandatory": false,
  "migrations": ["db:0012_session_memory"],
  "signature": "ed25519:…"           // подпись манифеста нашим ключом
}
```

Выбор «попадаю ли я в 10 %» — детерминированный: `hash(installId + version) % 100 < rollout*100`.
Так выкат расширяется без «повезло/не повезло» на каждом запуске.

**Подпись манифеста** (Ed25519, публичный ключ зашит в приложение) — защита от подмены, если
аккаунт GitHub или CDN скомпрометирован. Проверяем: подпись → домен URL → sha512 файла.

## 3. Что проверяем перед установкой

1. Подпись манифеста и `sha512` файла.
2. `semver`: версия новее текущей; `minSupported` не выше текущей (иначе — «слишком старая»).
3. Совместимость: ОС ≥ Windows 10 1809, архитектура, свободное место, версия БД (миграции
   вперёд-совместимы).
4. Не идёт ли задача: если идёт — «обновление готово, применю после завершения» (никогда не
   убиваем работу пользователя).
5. Целостность установки: если файлы приложения изменены — предупреждаем («похоже, установка
   повреждена, рекомендую переустановить»).

## 4. Установка и откат

- Скачивание в `%LOCALAPPDATA%/ZShelper/updates/`, докачка при обрыве.
- Установка: NSIS «тихая» (`/S`), перезапуск приложения после.
- **Бэкап данных** перед миграцией: копия `data.db` + `settings.json` в `backups/<version>/`.
- Миграции БД — только вперёд и идемпотентно; при ошибке — восстановление из бэкапа и откат
  на предыдущую версию (установщик предыдущей версии остаётся на диске).
- Кнопка «Вернуться на 1.3.0» в настройках (для отладки и для «новая версия сломала»).
- Отзыв версии: в манифесте `revoked: ["1.4.1"]` → приложение не устанавливает и сообщает.

## 5. Безопасность цепочки поставок

| Мера | Зачем |
| --- | --- |
| Подпись кода (EV/OV-сертификат или Azure Trusted Signing) | SmartScreen, доверие пользователя |
| `actions/attest-build-provenance` | доказуемо, что артефакт собран из этого коммита |
| SBOM (`anchore/sbom-action`) | прозрачность зависимостей |
| `SHA256SUMS` + подпись | ручная проверка для параноиков |
| Пиннинг версий зависимостей и lockfile | воспроизводимость |
| `harden-runner` + `dependency-review` в CI | защита от компрометации CI |
| Публичный ключ обновлений в приложении | защита от подмены манифеста |
| Только HTTPS + allowlist доменов | MITM |

## 6. UX обновлений

- Тихая проверка при старте (не блокирует), затем раз в 6 часов и по кнопке.
- Баннер: «Доступно обновление 1.4.0 — что нового» с человеческим списком (не CHANGELOG-простыня).
- Три кнопки: «Обновить сейчас», «При выходе», «Не сейчас».
- Прогресс с реальным размером и скоростью, возможность отмены.
- «Что нового» — с картинкой/скриншотом, если есть.
- После обновления — короткий экран «что изменилось» + «что сломаться не должно» (для отката).
- Полностью офлайн: проверка не мешает работе, ошибки сети не показываются как ошибки.

## 7. Распространение помимо GitHub Releases

| Канал | Плюс | Как |
| --- | --- | --- |
| Portable `.zip` | без установки, для «попробовать» | `electron-builder` portable; обновление — заменой папки с сохранением данных |
| `winget` | установка одной командой, обновления системным менеджером | манифест в `microsoft/winget-pkgs` (PR) |
| `scoop` bucket | то же для «продвинутых» | свой bucket-репозиторий |
| MSIX | корпоративная раскатка | `electron-builder` msix / `msix-packaging` |
| Зеркало | если GitHub недоступен | статический хостинг с тем же манифестом (подпись сохраняется) |

## 8. Версионирование и совместимость

- **semver**: MAJOR — ломаем формат данных/скиллов; MINOR — новые возможности; PATCH — фиксы.
- Поддержка: текущая + 2 предыдущих минорных (миграции умеют шагать через одну).
- Формат скиллов/манифеста моделей — с полем `schema`; читаем минимум 2 версии назад.
- `minSupported` в манифесте обновлений = «ниже нельзя» (например, из-за безопасности).

## 9. Метрики и обратная связь (без телеметрии по умолчанию)

- Локально: «обновление установлено», «откатился», «ошибка обновления» → видно пользователю.
- Опционально (явно включается): анонимный пинг «версия + ОС + успех/провал» — чтобы видеть,
  что 5 % установок падает. По умолчанию **выключено**.
- Владельцу проекта: GitHub Actions + issue-шаблон «проблема после обновления».

## 10. Чеклист релиза (встраивается в CI)

1. Тесты зелёные, evals не деградировали > 5 %.
2. Версия поднята (`release-please`), CHANGELOG собран.
3. Сборка подписана, SBOM и аттестация приложены.
4. `manifest.json` обновлён (rollout 10 %), подписан.
5. Дымовой тест на чистой ВМ (Win10 + Win11): старт, первый ответ, создание папки, обновление
   с предыдущей версии, откат.
6. Через 24 ч при отсутствии жалоб — rollout 100 %.

## 12. Открытые вопросы

- Дельта-обновления: blockmap в electron-builder работает, но требует одинаковой сборки; выигрыш
  60–80 % трафика. Проверить на наших размерах (~90 МБ).
- Свой манифест + GitHub Releases = две точки правды. Решение: манифест **ссылается** на релиз,
  а `latest.yml` оставляем как fallback, если манифест недоступен.
- Подпись кода без сертификата: SmartScreen будет пугать. Проверить SignPath (бесплатно для OSS)
  или Azure Trusted Signing (платно) — решить по бюджету.
- Нужен ли «канал для знакомых» (beta) с отдельным `appId`, чтобы не мешать stable? Гипотеза: да.
