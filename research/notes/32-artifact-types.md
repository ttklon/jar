# 32. Три вида артефактов: профиль, инструмент, класс работы

Этот конспект закрывает вопрос, который висел с самого начала: «профилей мало, давай профили
на всё». Ответ оказался не в количестве, а в том, что **не всякая способность выражается через
профиль приложения**. Пока этого не разделить, аудит покрытия будет вечно показывать долг там,
где долга нет, и прятать долг там, где он есть.

## Четыре артефакта вместо одного

| Артефакт | Что описывает | Пример | Чем проверяется |
| --- | --- | --- | --- |
| **Профиль приложения** (`kind: app`) | якоря, шаги, проверки в одной программе | DaVinci Resolve, Slack, Acrobat | прохождение операции в живом окне + `verify` |
| **Профиль-инструмент** (`kind: tool`) | командная утилита без интерфейса | `robocopy`, `psql`, `tshark`, `soffice`, `beet` | код возврата, лог, XML-отчёт, хэш |
| **Профиль-класс** (`kind: system`) | работа в самой Windows как «приложении» | устройства, безопасность аккаунтов, календарь | состояние системы (PnP, firewall, ICS) |
| **Скилл-рецепт** | последовательность моделей и документов без GUI | «дневник самочувствия», «резюме под вакансию» | качество результата, а не «нажалось» |

Первые три живут в `data/profiles/`, четвёртый — в `data/skills/` (формат и первые 10 рецептов
построены позже этой заметки, см. `docs/SKILLS.md`; в планах M3 остались ежедневные скиллы
оркестратора). Именно
поэтому в схему профиля добавлено поле `kind`: без него аудит не отличает «мы не сделали
устройства» от «устройства вообще не про окна».

## Почему остальные десять доменов — не профили

После этой итерации без профиля осталось 9 доменов из 49. Каждый классифицирован в
`data/domain_profile_policy.json`, и аудит падает, если появится домен без классификации.

**`smart-home` (16) — профиль сделан, и это профиль хаба, а не приложения.** Но профиль не приложения, а
**хаба**: Home Assistant API / MQTT / Matter. Сущности, состояния, сцены, проверка по `reported
state`, а не по «нажал на выключатель». Он лежит в `data/profiles/home-assistant.json` (`kind: system`) и закрывает семь операций: свет, сцены, расписание, «кто дома», наблюдение за датчиками, отчёт по энергии и замки (последние — только по прямой команде). Дальше — коннектор плюс пять сценариев: свет по
расписанию, сцена «ушёл», климат, датчик протечки, отчёт по энергии.

**`health-daily` (22) — сознательно не автоматизируем.** Медицинские приложения без API, а цена
ошибки — здоровье. Класс закрывается напоминаниями, дневником в markdown, разбором анализов через
OCR и модель, оценкой еды по фото. Ошибка в дозе лекарства не должна быть возможна в принципе,
поэтому здесь нет ни одной операции, которая «что-то нажимает в аптеке».

**`travel` (16) — деньги.** Билеты и отели: агент собирает, сравнивает, готовит ссылку; покупку
делает человек. Профиль здесь означал бы автоматическую оплату, а это зона `never` в реестре.

**`home-daily` (15), `languages` (14), `career` (14), `legal-docs` (13)** — информационные классы:
меню, сметы, переводы, произношение, резюме, разбор договора. Приложения для них — Word,
LibreOffice, Acrobat, браузер — и они уже покрыты профилями. Добавлять «профиль календаря
полива растений» бессмысленно: это скилл-рецепт, а не интерфейс.

**`ai-ml` (13) — внутренний домен.** Инференс, квантование, эмбеддинги, сравнение моделей. Его
«интерфейс» — рантайм (llama.cpp, ONNX Runtime, whisper.cpp), и проверяется он бенчмарками
(tok/s, RAM, качество на своём наборе), а не якорями.

**`licensing` (12) — наш собственный продукт.** Профиль тут — API VPS из `docs/LICENSING.md`:
`activate` / `refresh` / `deactivate` / `entitlements`. Проверка — интеграционные тесты и
негативные сценарии (истёкший токен, отозванный ключ, третий ПК).

**`superhuman` (20) — мета-домен.** 24/7, параллельность, память, восстановление после сбоя. Это
требования к архитектуре; они проверяются eval-набором (uptime, дедупликация алертов, лимиты
ресурсов), а не операциями в окне.

## Что даёт это разделение

1. **Аудит перестал врать.** Раньше строка «28 доменов без профиля» выглядела как провал, хотя
   половина из них — не про интерфейс. Теперь есть два списка: очередь (1 домен) и решения
   (9 доменов с причиной).
2. **Новые домены нельзя добавить молча.** Если в реестре появляется домен без профиля и без
   классификации, `tools/audit_actions.py` выходит с кодом 1.
3. **Стало видно настоящий долг.** Это не «профилей мало», а: 52 приложения tier A из 122 в
   каталоге, и 72 приложения, у которых профиля пока нет вовсе. Вот это и есть работа, а не
   домены.

## Цифры на момент написания

- профилей **58** (из них `app` — 47, `tool` — 7, `system` — 4), операций **344**;
- домены с профилями: **39 из 49**;
- домены без профиля: **9** — очередь пуста: все девять закрываются другим артефактом;
- приложений в каталоге **122**, tier A — **54**, профиль найден по процессу у **66**, без профиля — **56**.

## Правило, которое стоит запомнить

**Профиль нужен там, где есть интерфейс, который надо вести. Скилл нужен там, где надо получить
результат.** Путаница между этими двумя вещами — главная причина, по которой ассистенты умеют
«нажимать кнопки» и не умеют делать работу.
