# 09 — Кодинг-агент: «сделай мне программу» на реальной машине

Требования R-17…R-20. Это главная «большая» задача продукта, поэтому у неё отдельный
под-оркестратор и отдельный жизненный цикл.

## 1. Полный конвейер

```
[1] Требования     ──> бриф (цель, пользователи, функции, ограничения, критерии готовности)
[2] Исследование   ──> план поиска → источники → заметки → отчёт с ссылками
[3] Архитектура    ──> стек, структура, схема данных, риски, план этапов
[4] Каркас         ──> репозиторий, лицензия, линтеры, CI, первый запуск
[5] Реализация     ──> вертикальные срезы (фича + тест) в git-worktree
[6] Проверка       ──> сборка, тесты, линт, ручной smoke, скриншоты
[7] Итерации       ──> багфиксы по логам/скриншотам, ревью собственного диффа
[8] Сдача          ──> README, инструкция запуска, коммиты, отчёт, демо-скрипт
```

Ключевое: **шаг 1 и 2 не пропускаются**. Без брифа агент пишет «Hello World» вместо продукта,
без исследования — изобретает колесо.

## 2. Бриф (шаг 1)

Шаблон, который агент заполняет *вместе* с пользователем (голосом, 3–5 вопросов, не 20):

```md
# Бриф: <название>
Цель: <что должно стать возможным>
Пользователь: <кто, в каких условиях>
Функции v1 (must): 1) … 2) … 3) …
Не-цели: …
Ограничения: ОС, офлайн, без внешних сервисов, бюджет времени
Критерии готовности: <проверяемые!> — «exe запускается, импортирует CSV, показывает 3 графика»
```

Правило: критерии готовности — только проверяемые утверждения. «Удобный интерфейс» не
критерий; «две кнопки: Импорт и Экспорт, работают на тестовом CSV» — критерий.

## 3. Исследование (шаг 2)

Инструменты: `web.search`, `fetch`, `browser.read`, GitHub-поиск, документация через `context7`.
Процесс:
1. 5–10 поисковых запросов (агент сам формулирует, показывает список).
2. Отбор: официальные доки > первоисточники > статьи; дата < 12 мес.
3. Конспект каждого источника: 3–5 тезисов + ссылка + «насколько доверяем».
4. Отчёт: `research.md` в папке проекта, с разделами «варианты», «решение», «риски», «ссылки».
5. Артефакты сохраняются в `artifacts/<jobId>/sources/` — чтобы вернуться к ним через неделю.

Это ровно то, что мы делаем в этом vault — переносим ту же практику в продукт.

## 4. Архитектура и план (шаг 3)

Агент обязан выдать:
- выбранный стек + **альтернативы и почему отвергнуты**;
- структуру файлов (дерево);
- модель данных (если есть);
- план этапов с горизонтом «что можно запустить через 30 минут»;
- список рисков с mitigations;
- «что я НЕ буду делать» (границы).

Пользователь утверждает план (кнопка «Поехали») или правит. Только после этого — код.

## 5. Реализация: как писать код, который работает

### 5.1 Среда
- Каждый проект — отдельная папка в `workspace/<slug>/` + `git init` + первый коммит с брифом.
- **git worktree на задачу**: `workspace/<slug>/.worktrees/<taskId>` — параллельные задачи
  не мешают друг другу, откат = удалить worktree.
- Зависимости ставятся в **локальное окружение проекта** (venv/node_modules), не глобально.
- Терминал — через `node-pty`, с таймаутом и лимитом вывода (иначе сборка на 100 МБ логов
  убьёт контекст).

### 5.2 Цикл «правка → проверка»
```
read (repo map + целевые файлы)
  → propose patch (unified diff, минимальный)
  → apply (с проверкой контекста; при конфликте — перечитать и повторить)
  → run (build / test / lint) — только релевантное
  → на ошибку: читать ТОЛЬКО хвост лога + первый стектрейс
  → fix (≤ 3 попытки, потом пересмотр подхода / вопрос пользователю)
```
Правила, которые резко повышают успех:
1. **Один логический шаг = один патч = один коммит** (с осмысленным сообщением).
2. **Всегда читать перед правкой** — не «писать по памяти».
3. **Не переписывать файл целиком**, если меняется 5 строк.
4. **Тесты раньше кода** для новых функций (TDD-режим включается).
5. **Никогда не «глушить» ошибку** (`try/except: pass`, `--no-verify`) без явного согласия.
6. **Не добавлять зависимость**, если задачу решает stdlib (и наоборот — не писать 500 строк
   вместо 20 при зрелой библиотеке).

### 5.3 Repo map (экономия контекста)
- Дерево файлов с размерами + языками.
- Символы (функции/классы) через tree-sitter по нужным файлам.
- «Карта важности»: файлы, которые менялись в задаче, точка входа, конфиги, тесты.
- Внешние инструменты: `repomix`, `gitingest` (см. vault), `serena` (LSP-навигация),
  `aider` (repomap-подход) — берём идеи, не зависимости.

## 6. Длинные сессии и восстановление (R-19)

| Механизм | Как |
| --- | --- |
| Чекпойнт | после каждого зелёного теста: план + статус + следующий шаг в `job_steps` |
| Восстановление | после краха: git status + последний чекпойнт + повтор незавершённого шага |
| Ротация контекста | каждые ~20 шагов — суммаризация («что сделано, что осталось, где грабли») |
| Бюджеты | время/токены/диск; при исчерпании — «пауза, продолжить?» (голосом или в Telegram) |
| Heartbeat | в Telegram раз в 15–30 мин: «этап 3/7, тесты 12/14, ошибок нет» |
| Стоп | голос/хоткей/кнопка → сохранение состояния и корректное завершение |

## 7. Специфика Windows

- Пути с пробелами и кириллицей → всегда кавычки; проверять `chcp`/кодировку вывода (cp866!).
  Вывод консоли декодировать как `utf8 → cp866 → cp1251` с эвристикой.
- `npm`/`npx` на Windows — `.cmd`; запускать через `shell: true` только с массивом аргументов
  (иначе инъекция).
- Docker может отсутствовать → сценарии не должны требовать его.
- Visual Studio Build Tools нужны для нативных модулей → проверять и подсказывать.
- Долгие пути (`node_modules/.bin/...`) → `\\?\`.
- Antivirus может медленно сканировать `node_modules` → исключение для workspace (с согласия).
- Python: `py -3` вместо `python`; venv в `.venv`; `uv` если доступен (быстрее в 10×).

## 8. Сопровождение после сдачи

- `README.md` + `run.cmd` (один клик) — обязательно.
- Скриншот работающего приложения → в отчёт.
- «Как продолжить завтра»: список следующих задач (бэклог), сгенерированный из TODO и
  заметок по ходу.
- Папка проекта открывается в Explorer по кнопке в UI.

## 9. Метрики качества кодинг-агента (см. `15-evals.md`)

| Метрика | Цель v1 |
| --- | --- |
| Доля задач с «зелёным» запуском с первого прохода | ≥ 40 % |
| Доля задач, доведённых до работающего состояния за ≤ N шагов | ≥ 70 % |
| Среднее число шагов на задачу | ≤ 15 |
| Доля патчей, отклонённых (конфликт/не применилось) | ≤ 10 % |
| Регрессии (сломал ранее работающее) | ≤ 5 % |
| «Молчаливые» подавления ошибок | 0 |

## 11. Открытые вопросы

- «Действия кодом» (CodeAgent) для кодинга — да; но нужно ограничить импорты и сеть в песочнице.
- Нужен ли собственный «архитектор» (отдельная модель, которая только ревьюит диффы)?
  Гипотеза: да, на T2+; на T1 — самопроверка по чеклисту.
- Как обрабатывать задачи, где нужен GUI (например, «сделай Electron-приложение и проверь,
  что окно открывается»)? Нужен headless-проверка через Playwright + скриншот окна.
