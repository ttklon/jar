# 12 — Коннекторы: календарь, почта, Telegram, заметки и «всё остальное»

Требования R-11, R-21. Принцип: **коннектор — это инструмент с явными правами**, а не
«магическая интеграция». Пользователь видит, к чему у приложения есть доступ, и может отозвать.

## 1. Каталог коннекторов (v1 → v2)

| **Gmail** | читать/искать/отправлять | OAuth 2.0 + scopes | ★★★ |

| **Slack** | сообщения, каналы | bot token | ★★ |

Для каждого — **MCP-сервер или встроенный коннектор**, но интерфейс один: реестр способностей.

## 2. Авторизация: как не потерять токены

- OAuth 2.0 **Authorization Code + PKCE**, loopback-редирект на `127.0.0.1:<random>` —
  стандартный путь для десктопа, без встроенного браузера.
- Токены — только в Windows Credential Manager (DPAPI через `safeStorage`), никогда в JSON.
- Refresh-токен обновляется в фоне; при отзыве — понятное сообщение «нужно переподключить».
- **Минимальные scopes**: не просим `gmail.modify`, если нужно только читать.
- Экран «Доступы»: список, дата выдачи, «отозвать», «проверить».
- Никакой телеметрии: токены и данные не уходят никуда, кроме соответствующих API.

## 3. Календарь (пример полного коннектора)

Инструменты: `calendar.listEvents(range)`, `calendar.createEvent(...)`, `calendar.updateEvent`,
`calendar.deleteEvent`, `calendar.findFreeSlot(duration, window)`, `calendar.remind(...)`.

Особенности, которые обычно забывают:
- **Часовые пояса**: храним ISO-8601 с offset; «в пятницу в 15:00» = локальное время ПК
  (Europe/Stockholm), а не UTC.
- **Повторы (RRULE)**: создание повторяющегося события — отдельная логика, не «10 событий».
- **Приглашения**: если добавляем участников — это `external` риск (человек получит письмо).
- **Конфликты**: перед созданием проверяем пересечения и спрашиваем «пересекается с …,
  всё равно?».
- **Оффлайн**: если сети нет — кладём в очередь и создаём при появлении связи, с уведомлением.

Голосовой диалог, который должен работать:
> «Поставь встречу с Андреем в пятницу в три» → «В пятницу 14-го в 15:00, на час, добавить
> Андрея и отправить приглашение?» → «Да» → «Готово, приглашение отправлено. Напомнить за час?»

## 4. Telegram (двойная роль)

1. **Канал уведомлений** (`10-safety.md` §6) — самое ценное: пользователь вдали от ПК видит,
   что делает агент, и может остановить.
2. **Пульт управления**: команды `/status`, `/stop`, `/pause`, `/report`, `/run <задача>`,
   голосовое сообщение → ASR → задача (отправка голосового себе в бота — нативный «ввод
   с телефона»).

Технические детали:
- Long polling (`grammY`), webhooks не нужны → работает за NAT без белого IP.
- Привязка чата одноразовым кодом (6 цифр, TTL 5 мин), иначе бот игнорирует всех.
- Rate limits Telegram: ≤ 30 сообщений/с, но по одному чату ~1/с → батчинг алертов («5 шагов
  за минуту» одним сообщением).
- Формат: короткие сообщения, HTML-parse mode, без «простыней»; детали — по кнопке.
- Файлы: скриншоты, логи, PDF-отчёты — до 50 МБ.

## 5. Заметки и «второй мозг»

- Obsidian: пишем `.md` в vault (с фронтматтером: `created`, `tags`, `source`), уважаем
  существующую структуру папок, не перезаписываем без подтверждения.
- Notion: страницы/базы через API; кэш только метаданных.
- Встроенные заметки: `notes/<date>.md` — «дневник дня» (что делали, что решили), генерируется
  из аудита; это дешёвая и очень полезная функция.

## 6. Почта: осторожно и явно

- Чтение/поиск — `read`.
- Черновик — `write-local` (безопасно! создаём draft, не отправляем).
- Отправка — `external` + показ точного текста и получателей; голосом не подтверждаем.
- Никогда не удаляем письма автоматически; «архивировать» максимум.
- Вложения: скачиваем только по запросу, проверяем размер/тип, не открываем «.exe/.lnk».

## 7. Локальные файлы как «коннектор»

Самая частая задача — не API, а файлы. Поэтому:
- индексируем выбранные папки (Документы, Рабочий стол, проекты) с согласия;
- поиск: имя (fuzzy), содержимое (FTS), дата, тип; «найди мой договор от марта»;
- операции: открыть, показать в проводнике, переслать в Telegram, приложить к письму.

## 8. Что НЕ подключаем в v1

Банки, госуслуги, любые сервисы с 2FA/капчей — там агент бессилен и опасен. Вместо этого —
«навигатор»: открывает нужную страницу, подсвечивает поля, но ввод и подтверждение — руками
пользователя. Честность лучше ложных обещаний.

## 9. Архитектура коннектора

```ts
interface Connector {
  id: string;                          // "google.calendar"
  auth: "oauth2" | "token" | "none" | "file";
  scopes?: string[];
  tools: Capability[];                 // риски предзаполнены
  health(): Promise<"ok" | "needs-auth" | "error">;
  connect(): Promise<void>;            // открывает браузер, ждёт loopback
  disconnect(): Promise<void>;         // отзывает + чистит токены
  rateLimit?: { perMinute: number };
}
```

Коннектор не имеет права напрямую дергать сеть из ядра: сетевые вызовы идут через
`net.http`-инструмент, который логирует домен и уважает allowlist → единая точка аудита.

## 11. Открытые вопросы

- Google OAuth в «неопубликованном» приложении требует верификации для чувствительных scopes
  (Gmail) → пользователю придётся создавать свой OAuth client. Как сделать это максимально
  просто (мастер на 6 шагов со скриншотами)? Или использовать «свой client id» + инструкция.
- Нужен ли встроенный CalDAV-клиент (универсально для Яндекс/Nextcloud/Mail.ru)? Скорее да —
  это дешевле, than 5 разных OAuth-провайдеров.
- Яндекс.Календарь/Диск: популярно в РФ, поддерживает OAuth — стоит сделать в v1.1.
